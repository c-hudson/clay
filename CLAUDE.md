# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Critical Rules

**All UI changes must be reflected in ALL interfaces.** Any new field, option, or window added to one interface (console TUI, web, webview-GUI, and the native GPUI GUI in `src/native_gui/`) must be added to all of them (the SSH remote console shares the console TUI's renderer, so it usually follows for free). New world/settings fields must also be saved to `~/.clay/settings.dat` in `persistence.rs` and loaded on startup and `/reload`.

**World passwords are stored encrypted in `~/.clay/settings.dat` but sent as plaintext to authenticated WebSocket clients and displayed as readable text in all UI editors.** Do not hide or mask world passwords in the world editor — the encryption is for at-rest storage only. The `has_password` field mirrors whether the password is non-empty.

**Do not write to stdout/stderr once the TUI is initialized (no `println!`, `eprintln!`, `dbg!`).** The rule exists because such output corrupts the ratatui screen (scroll regions, separator bar) after it's been drawn. It does NOT apply before the TUI is initialized, nor in headless contexts that never draw a TUI — startup/config messages before the alternate screen is entered, the `-D` daemon and `--multiuser` server (both headless, including the interactive first-run wizard's operator output), and the panic hook during teardown may use `println!`/`eprintln!` normally. Once the TUI is live, use instead:
- `debug_log(true, msg)` for always-on logging (writes to `~/.clay/debug.log`)
- `debug_log(is_debug_enabled(), msg)` for user-toggled debug
- `output_debug_log(msg)` for output/seq debugging (writes to `~/.clay/output.debug.log`)
- `add_tf_output()` to display messages in the output area

Debug output interferes with the TUI and corrupts the terminal display *once the TUI is live* (see the exception above for pre-init/headless/panic contexts). When the TUI is running, instead:
- Use `debug_log(true, msg)` for always-on logging or `debug_log(is_debug_enabled(), msg)` for user-toggled debug (writes to `~/.clay/debug.log`)
- Use `output_debug_log(msg)` for output/seq debugging (writes to `~/.clay/output.debug.log`)
- Display messages in the output area using `add_tf_output()` or `add_output()`

## Build Commands

```bash
# Default build command (always use this)
cargo build --target x86_64-unknown-linux-musl --no-default-features --features rustls-backend,ssh-transport
# Output: target/x86_64-unknown-linux-musl/debug/clay

cargo build --features webview-gui   # Build with webview GUI client (ssh-transport included via defaults)
cargo test                           # Run all tests
cargo test test_name                 # Run a single test
cargo clippy                         # Lint
```

**Why musl:** glibc static builds cause SIGFPE crashes during DNS resolution. **Why rustls:** native-tls requires OpenSSL cross-compilation for musl.

**`ssh-transport`** (SSH-tunneled `--console`/`--gui`, see `src/ssh.rs`) is in `[features] default` in `Cargo.toml`, so any build WITHOUT `--no-default-features` gets it automatically. Any `--no-default-features` invocation must add it back explicitly or the binary silently loses `--ssh`/`--ssh-proxy` support (`--ssh` exits with "requires the 'ssh-transport' feature" instead of erroring on something more obviously wrong) - this bit us once already; if you add a new `--no-default-features` build command anywhere (a script, this doc, CI), include `,ssh-transport`.

### Cross-Platform Builds

- **Termux:** cross-compiled with the Android NDK, no phone needed: `./build-termux-aarch64.sh` / `./build-termux-armv7.sh` (no GUI) and `./build-termux-aarch64-gui.sh` (webview GUI - links against Termux's own packages unpacked by `tools/termux-sysroot.py`, applies the tao/wry X11 patches in a throwaway worktree). No hot reload, TLS proxy, or Ctrl+Z on Android.
- **macOS:** `cargo build --no-default-features --features rustls-backend,ssh-transport` (no musl). Universal binary via `lipo` combining x86_64-apple-darwin and aarch64-apple-darwin targets.
- **Windows:** `set RUSTFLAGS=-C target-feature=+crt-static` then `cargo build --release --features webview-gui` (MSVC, not cross-compiled)

## Architecture

Clay is a terminal-based MUD client built with ratatui/crossterm for TUI and tokio for async networking. Supports multiple simultaneous world connections with SSL/TLS.

### Key Structs

- **App**: Central state - worlds, input area, spell checker, settings, popups, keybindings, TF engine
- **World**: Per-connection state - output buffer, scroll position, connection, unseen lines, pause state, prompt
- **InputArea**: Input buffer with viewport scrolling, command history, cursor position, kill ring
- **PopupManager**: Unified popup system for all modal dialogs
- **WebSocketServer**: Embedded WebSocket server for GUI/web/remote console clients

**Chat worlds (Slack/Discord):**

User docs: `docs/markdown/21-chat-worlds.md`.

**Shell worlds (`WorldType::Shell`):**
- `src/shell/` - a world that is a local terminal (PTY + `alacritty_terminal`). `mod.rs` (`ShellSession`: the `Term` + event loop + a wrapper thread for bounded teardown; the `Proxy` that forwards emulator events as `AppEvent::Shell`), `screen.rs` (`ShellScreen`: render the grid to ANSI rows + a plain projection, track dirty rows and a lockstep frame counter, build/apply full & delta frames; activity = a cell gained a non-space char), `keys.rs` (one xterm key encoder + the shared `classify` carve-out), `app.rs` (`App` glue: connect, read the screen, activity, input, per-viewer sizing, frame coalescing, exit). Clients render the screen with their existing line pipeline (console `render_shell_crossterm`, native `shell_output`+`OutputSnapshot.shell_cursor`, web `renderShellScreen`). Wire: `WsMessage::ShellScreen`/`ShellInput`/`ShellMouse`, `WorldStateMsg.shell`. User docs: `docs/markdown/23-shell-worlds.md`. Three rules that bite: the `Proxy`'s `send_event` is called under the `Term` lock onto a bounded channel, so it must `try_send` only and never touch the `Term` (coalesce the wakeup); teardown runs on the wrapper thread (the PTY's `Drop` blocks); `platform::reap_zombie_children` must be `waitpid(0)` (our process group), not `-1`, or the PTY child's exit is stolen and the emulator loop spins. A shell world's output never enters `output_lines`, the log, the archive, TF or triggers. Multiuser refuses shell worlds. Two more: every way a client connects a world through `daemon::handle_daemon_ws_message` (the `-D` and GUI-master handler: `/worlds <name>` - which is what TF's `/connect` becomes - `/worlds -b`, `ConnectWorld`) goes through `start_non_mud_world` first, because the daemon's own MUD connect dialled a shell world's empty address ("Connecting to :...") while the console's path (commands.rs) knew the type; and a client rejecting a delta asks for the full screen **once** (`ShellScreen::awaiting_full`) - every delta still in flight is stale too, and each used to cost another request and another full frame. After `/reload` re-attaches a shell (`adopt_shell_worlds_after_reload`), the program's repaint - the size nudge, the injected "[Clay reloaded]" note - is not activity: `ShellScreen::ignore_activity_until` holds `gained_printable` down for two seconds, or every reload lit a background shell world's indicator.

**Theme:**
- `src/theme.rs` - ThemeColors (42 customizable color vars), ThemeFile for `~/.clay/theme.dat`. GUI/web only; console uses Theme enum from encoding.rs. The GUI theme is a **name** (`Settings.gui_theme: String`, always `theme::normalize_theme_name`d): one of `theme::BUILTIN_THEMES` (`dark`, `light`, `dark-new`, `light-new`, each with its picker label) or a custom `[theme:name]`. "Is this a light theme" is `ThemeColors::is_light()` (background luminance), never a name check — the native tile mix, the WebView's window theme and app.js's `body.theme-light` all derive from it. The three pickers (console `/setup`, web Settings, native Settings) list `BUILTIN_THEMES`. **The web client's chrome is the native GUI's, in theme-independent CSS** (style.css "Cards, sidebars and tiles" / "Buttons": `.card`/`.card-frame`/`.card-stack`, `.sidebar` + `.side-tile` (icon+label; `body.device-phone` makes it an icon strip), one `.btn`/`.btn-primary`/`.btn-danger` family with the primary's text in `var(--theme-bg)`, never a hardcoded cyan; selected rows = accent on bg text; the hover tints `--accent-hover`/`--hover-lift` and translucent `--fg-7`/`--accent-14` have `@supports` fallbacks). app.js `applyThemeAppearance()` is the web `is_light()`: it reads the computed `--theme-bg` back, so it runs AFTER `applyThemeColors`/`ThemeCssVarsUpdated` write the variables, and tells the Android app (`Android.setThemeAppearance(bg, light)`) so the system bars follow. The three editor pages get `{{THEME_CSS_VARS}}` too (http.rs) and map their `--editor-*` palette onto `--theme-*`. Android caches the page's `:root { … }` rule (`saveThemeCss`) and injects it as declarations at a cold start - the Java side strips the `:root {` wrapper; wrapping it again produced invalid CSS and the cached theme never applied. The theme's **name** is on the page too (`body[data-gui-theme]`, app.js `markGuiTheme`, remembered in localStorage for that cold start) for rules that belong to one built-in theme rather than to its colours: by user ruling (2026-10-16) Dark - New's phone nav bar (`body.device-phone[data-gui-theme="dark-new"] #nav-bar > *`) keeps the original Dark buttons and slider on Dark - New's own bar, and the phone's input area (`#input-container`) takes Dark's ground and top line; tablets keep Dark - New's. Restate the `--text-color`/`--border-color`/`--accent-color` aliases in such a rule: they are resolved at `:root`, so overriding only the `--theme-*` behind them changes nothing.

**Data Files** (all inside `~/.clay/` on Unix, `~/clay/` on Windows):
- `settings.dat` - Main settings (INI format with `[global]` and `[world:name]` sections)
- `secure.key` - Per-machine AES-256 encryption key (binary, 0600 permissions)
- `known_hosts.dat` - Trust-on-first-use TLS certificate pins (`host:port` -> hex SHA-256 of the end-entity cert DER), 0600 permissions. Written by `persistence::add_pin`/`replace_pin`, read by `persistence::get_pin`; enforced by `platform::danger_rustls::TofuVerifier` (rustls MUD/remote-console/WebView-proxy connections) and `platform::check_native_tls_peer_pin` (native-tls MUD path). Both halves of an entry are lower-cased (`persistence::normalize_pin_host`, applied in every accessor *and* in the loader so older mixed-case entries migrate rather than strand): hostnames are case-insensitive, so `MyHost:9000` and `myhost:9000` must be one pin — two pins means a rotated cert is only caught for whichever spelling was used first. Android's `CertPinning.java` — a genuinely separate implementation of this same TOFU model — has always lower-cased here; keep the two in agreement. SSH host keys share the file under `ssh:{host}:{port}` (`ssh.rs::host_key_pin_key`), which is also safe to fold.
- `theme.dat` - Theme colors (INI format with `[theme:name]` sections; the four built-ins are always present, a file predating one still gets it at its defaults)
- `keybindings.dat` - Keyboard bindings (INI, only non-default bindings saved)
- `multiuser.dat` - Multiuser server settings
- `scrollback.db` - SQLite long-term scrollback archive. Schema v2 (`PRAGMA user_version = 2`): `worlds(wid, world_uuid, name, next_wseq, orphan)` as a dimension table, `output_log(id, wid, wseq, ts_ms, line_raw, gagged)`, `output_fts` (FTS5, **contentless**), `archive_meta`. A pre-v2 file is converted on first open by `migrate_to_v2` on the writer thread — build-alongside, row-count gate, then one atomic swap, so a reader never sees a torn pair and a failed migration degrades to the old behaviour rather than to an empty archive. `user_version > 2` is refused outright. Traps: the legacy `output_fts` must be dropped **before** the table rename (FTS5 keeps its `content=` link in its own config table, which `ALTER TABLE RENAME` does not rewrite); `'rebuild'` does not work on a contentless table, so the index is built row by row; and `line_text` is gone — the stripped form is recomputed (`search` already did this) and fed to FTS instead.
- `cert.pem` / `key.pem` - Auto-generated TLS cert/key for `web_secure` mode
- `debug.log` - Debug logging (via `debug_log()`)
- `output.debug.log` - Output/seq debugging (via `output_debug_log()`)
- `remote.log` - Remote connection events (silent drops, gate/knock outcomes, bans, WebSocket auth attempts)
- `dump.log` - `/dump` debug state output
- `settings-audit.log` - Debug-mode-only audit trail of `[global]` settings changes: old→new values, source client (web/gui/console/android/local), and a backtrace (via `persistence::save_settings_with_source()`, only written when debug mode is on)
- `logs/<WorldName>.<YYYY-MM-DD>.log` - Per-world session logs (when log_enabled)
- `media/` - Downloaded media cache

### Key Design Patterns

- **Borrow checker with App**: Clone data out of App before mutable borrows (e.g., ThemeColors, world info for WebSocket)
- **WebSocket InitialState**: `build_initial_state()` sends only `output_lines` (NOT pending_lines) to avoid duplicates. Partial lines excluded from broadcasts.
- **Hot reload**: `exec()` replaces process, TCP socket fds preserved via cleared FD_CLOEXEC. TLS connections need proxy process. The `CLAY_HTTP_LISTENER` env var / Windows listener-socket-handle-passing (`platform.rs`, `start_http_server`'s `inherited_handle` param) is now dormant for the GUI path — since D8 (see below) the GUI always uses the always-TLS-capable `start_https_server`, which doesn't wire it up, so Windows GUI reload relies on `start_https_server`'s existing bind-retry-with-backoff loop instead (same mechanism Unix always used). That retry only works because the listener and accepted sockets are made non-inheritable (`platform::not_inherited`): Windows sockets, tokio's included, are inheritable by default, so the reload successor used to inherit the old listener, which then held the port it needed to bind. Every reload in v1.6.25's Windows GUI ended Clay that way. A GUI's successor is also spawned with null stdio + `CREATE_NO_WINDOW`: after `FreeConsole` the std handles are stale, and inheriting them could make the spawn fail. `webview_gui.rs`'s duplicate-instance probe detects a reload via the `--reload` arg (always present on a reload exec), not `CLAY_HTTP_LISTENER` — don't revert that or the probe false-positives "already running" and aborts the reload.
- **GUI mode**: Default on Windows/macOS (no flag needed). `--gui` is the native GUI (`src/native_gui/`, `native-gui` feature, Rust >= 1.98; alone it runs Clay in-process via `native_gui::start_clay`, which mirrors `run_master_webgui`; `--gui=host` attaches) and is the platform default when built in; `--web-gui` is the WebView GUI, which `--gui` also opens in a build without `native-gui` (Termux). Both GUIs' "is the port free?" check binds `127.0.0.1` **and** `0.0.0.0`: Windows lets a loopback bind succeed beside another program listening on all interfaces, so the loopback alone let a Clay already running through to a server that couldn't bind - "did not come up on port 9000 within 10 seconds" (and the console's "Failed to start HTTPS server"). A bind failed with address-in-use names the holder (`platform::port_owner`, netstat + tasklist on Windows; `http::bind_failure`), and `GUI_HTTP_FAILED` lets the GUIs' start-up waits report a server that couldn't start at once. **Quitting either GUI runs `/quit`'s cleanup in the Clay it carries** (`quit_in_process_clay` → the headless loop's `GUI_QUIT` arm → `App::quit_cleanup`, the same method the console's `/quit` uses: archive flushed, TLS proxies ended, UPnP mapping returned), bounded at 5 s, before the process ends; the native GUI then `process::exit`s as tao does for the WebView. Without it each TLS proxy took the GUI's going for a hot reload and lived a minute (the proxy waits 60 s for its client to come back), its MUD connection open - "takes forever for the exe to quit". A reload must never go through this path. The release GUI assets carry both. The WebView master mode uses `run_master_webgui()` → `run_app_headless()`. `http_enabled=true`; the server is always TLS-capable (D8) but the WebView connects to `ws://127.0.0.1:<http_port>` (plain — localhost is always served unencrypted, see Connection Security below). **Both GUIs log their window in with the web password saved in settings.dat when there is one** (`gui_session_password` → `WsOverride::Saved`), so phones and browsers can log in with the one the user set in Settings > Web; only without one do they make a per-start random session password (`WsOverride::Session`), which `App::session_ws_password` keeps `write_settings_dat` from saving - it used to be made at every start regardless and saved, so the user's password was ignored at the next start and overwritten on disk, locking other devices out. Android's `--local-server` password is a session one too (the app keeps it in its prefs).
- **Native GUI: `ClayView::after` applies the core's effects itself.** A `core` call (`self.session.core.x()`) returns effects - `Effect::Send` among them - and `after` runs them through `Session::apply` (which is what sends, or hands a follower's message to its leader) before showing the rest, so `self.after(self.session.core.x(), cx)` is complete on its own and the older two-step `let rest = self.session.apply(fx); self.after(rest, cx)` still works. Before this, `after` only knew display effects: a shell world's keys (`shell_key`/`shell_text`/`shell_paste`) went to it unapplied and were never sent, in every build from v1.7.0 to v1.7.5 - the prompt showed, typing did nothing.
- **Native GUI: what `ClayView::later` queues runs at the window's next frame, so a close must be queued too, never decided by `is_open` at call time.** Dialogs open through `later` (they need the main window's `Window`); `close_dialog` used to queue a close only if the dialog was already open, so a reconnect that went connecting → online between two frames (a few ms on a LAN; a background window draws even less often) skipped the close and then opened "Connecting to Clay Server" over a working connection for good. The snapshot harness can't show such races by itself (headless GPUI draws whenever it settles): `open:connect-race` feeds the two states with no frame between; `tick:` runs the view's clock and `peek:` reports without drawing.
- **Native GUI: a `/window` (follower) shares the main window's connection, so the server sees one client with one world on screen.** A follower's `MarkWorldSeen`/`UpdateViewState` are dropped (`session::is_upkeep`) - sending them would move the main window's view, history and ▶ claims - so the main window reports its followers' worlds instead (`ClayView::report_other_views` → `OtherViews` → `App::handle_other_views`, a per-client `ws_client_other_views` that `ws_client_viewing` consults; a newly listed world is `mark_seen`). Without it a world brought up in a follower stayed unseen on the server, and Unseen First sent the follower back to it from every other world: Up/Down there bounced between two worlds and never reached the one with activity. It goes only to a server whose `InitialState.other_views` is true: **a server closes the connection on any message it can't parse** (`WS-BAD-MESSAGE`, then `break`), so a new client→server message sent unconditionally - and re-sent after every login - would keep a new GUI disconnected from an older server. Gate any new one the same way.
- **Native GUI more-mode (`ui/more.rs`): scrollback replies are never arrivals, nothing is drawn below a held line, and it counts rows.** A cold start from the disk cache catches up by gap fill, which `on_scrollback` appends at the tail exactly where live output goes - so every line from a scrollback reply carries `Line::scrollback`, and `MoreMode::arrivals` neither counts nor pauses on it (app.js's gap-fill branch bypasses `handleIncomingLine` the same way); without it the ~300 lines that arrived while the GUI was closed paused after a screenful and the window opened hundreds of lines back. Once paused, every line is held (client lines too, as app.js queues them) and `visible_lines` stops at the first held line: holding only the MUD's lines left an action's `/echo` lines drawn below the hold, pinned at the bottom while Page Down released lines in above them ("half a window at a time, the bottom half unchanged"). The pause threshold and releases are row budgets (`core::wrap::rows_in_columns`, the layout's wrap in whole columns), and a release spends this window's own held lines before asking the server (`ReleasePending`) for the rest. app.js follows the same two rules (`handleIncomingLine`/`releaseLines`, rows from `lineRows`, the server's own estimate of a line at the client's width): before, it paused and released by LINES - a screenful of wrapped prose overflowed the view - and asked the server in the same press it released its own, whose `PendingReleased` (a LINE count, still honoured: another interface's release shows as many held lines here) then released that many more. **More-mode is per world in both clients, as on the console** (`ClayView::more`, a `MoreMode` per world name, fed for every world in `follow_world`; app.js `worlds[i].more` via `moreOf`): every world's arrivals are counted and held in the viewer's own rows whether or not it is on screen, a switch shows the world's own held state, leaving a world counts afresh only when it holds nothing (`MoreMode::left`, the console's `switch_world`), and nothing is held at a connect (the server's `pending_count` stands in, so the cold-start rule above still holds). Before this only the shown world was counted and a switch dropped the hold, so a 50-line backlog came out all at once on the phone (user report 2026-10-23); the server pages a world nobody views against the console's screen (`viewer_output_dims`), which is why the client's own hold is what pages it.
- **The output's scroll bar is drawn the same everywhere on a desktop** (native `ui/output.rs`, every window; style.css `body.device-desktop #output-container`): an 8px thumb 1px from the edge in fg-muted (fg-secondary under the mouse), no track, its strip reserved even when nothing scrolls so the text never rewraps on the first overflow. Two traps. In the browser engines, the standard `scrollbar-width`/`scrollbar-color` beat the `::-webkit-scrollbar` pseudo-elements wherever both are known: left set, WebKitGTK (the Linux WebView GUI) drew GTK's own 21px trough, so they are unset under `@supports selector(::-webkit-scrollbar)` and only Firefox keeps them. In the native GUI, a thumb drag *replaces* `Scroll::pending` (`drag_thumb_to`): the thumb's place is absolute, and two mouse moves between frames, each measured from the same last layout, used to add up. - **Remote clients dedup output by exact seq membership, not a high-water mark** (PROTOCOL-ROADMAP.md Phase C). `app.js` tracks `world._seenRanges` — coalesced inclusive ranges of every seq the server has delivered — and drops a line only when its exact seq is already present (`hasSeenSeq`/`hasSeenRange`). Record ranges for the whole delivered batch span, never per surviving line, or client-side display filtering punches phantom holes. The server independently audits each client's `PongCheck.acked` against `World::deliverable_high_seq()` (`App::audit_client_acks`) and pushes `ResyncRequired` at a world stalled across two keepalives — so a *new* poisoning path self-heals instead of needing a fifth round of one-path-at-a-time fixes. - **The ▶ new-text indicator is owned per line, per viewer** (PROTOCOL-ROADMAP.md Phase D). `OutputLine`/`TimestampedLine` carry `viewed: bool` + `display_id: Option<u64>`; a client draws ▶ iff `display_id` is its own id (`InitialState.your_display_id`, derived from the stable `AuthRequest.client_uid` so it survives a reconnect). A line arriving while anyone is viewing is born `viewed` and can never be ▶ for anybody; the first client to *display* an unviewed line claims it, and the `!viewed` latch means a second client neither steals nor clears that marker. Claims/releases go to **one** client (`ClaimedNew`/`ReleasedNew`), never broadcast — that broadcast is exactly what made the old shared `new_from_seq`/`viewed_from_seq` watermark wipe other clients' markers on every world switch. Two traps: unviewed lines are **not** a contiguous tail (`viewed` flips with who's watching), so a claim must sweep the whole buffer and `ClaimedNew` must carry a seq list rather than a range; and backgrounding is **not** a disconnect (Android keeps the socket open), so it must be signalled via `ClientVisibility` — `WS_VIEWER_GRACE` is 10s and only covers transport blips. **`ClientViewState.visible` and `ClientViewState.paused` are not interchangeable**: both keep a client out of `ws_client_viewing`, but `paused` means only `/remote --pause` and is reported back to the client as its `PAUSED` badge by `handle_request_state`. Backgrounding writing into `paused` (as it briefly did) makes a resync landing in the background window light that badge with nothing to clear it on return. **A client must never hold a marker the server doesn't** (user report 2026-10-19: lines stayed ▶ however often the Android app switched away and back): leaving a world releases only what the server holds, so such a marker never clears. Three ways it happened: the reaper released an expired connection's markers though the same owner had reconnected - a reconnect is a new connection under the same owner id, so `reap_stale_ws_client_worlds` now skips an owner that is back; a release told only the connection that asked, though two can share an owner id (an Android `/window`, browser tabs: one localStorage `client_uid`), so `release_world_for` tells every live connection of the owner; and a client keeps its own lines across a reconnect and in its disk cache, old markers included, so `WorldStateMsg.own_new_seqs` lists every line the client owns, sent or not, and app.js `setOwnMarkers` / native `set_own_markers` apply it.
- **`OutputLine::archive_seq` (`wseq`) is NOT `OutputLine::seq`.** The protocol `seq` restarts at 0 on every cold start (`World::new` seeds it from `output_lines.len()`; only the hot-reload state file persists it, never settings.dat), `build_archive_prepend` fabricates values counting *backwards*, and daemon/multiuser emits 0 — so it is useless as a database key and `World::seq_epoch` exists precisely to disambiguate it. `wseq` is a separate, durable, per-world counter owned by the archive: reserved in blocks of 65 536 under `BEGIN IMMEDIATE` (so two Clay processes get disjoint blocks), `i64` end to end (SQLite INTEGER is signed; never use `u64` on this path), capped at 2^53 so it stays JSON-safe. A restart burns the block's remainder, which is fine because every consumer compares with `<`, never `== previous + 1`. Producers stamp it synchronously (`World::archive_line`) because a line must know it the instant it lands in `output_lines`; when the allocator is unreachable the writer assigns one instead — losing the number is acceptable, losing the line is not.
- **Only non-partial server lines are archived, and the completion branch must archive too.** `add_output`'s partial-completion path updates the line in place and returns `1` to skip it in the loop where archiving happens, so for a long time any line split across two TCP reads was **never archived at all**. It archives there now, gated on `from_server` (that branch does not otherwise know, and client text must not be archived) and on the line actually being complete.
- **FTS is a candidate filter, never the answer**, and it is used only when the term is *selective*. Every candidate is still matched by the Rust regex, so over-matching is harmless while under-matching is a silent wrong answer — hence `RecallMatchStyle::Simple` (a *substring* match, versus FTS's whole-word tokens) and any leading/internal wildcard never route. A term matching most rows makes the candidate set enormous and is measurably *slower* than the plain range scan (131ms vs 17ms), so `FTS_SELECTIVITY_CAP` probes the candidate count and falls back. Realistic selective searches went 102ms → 11ms on a 100k-row world.
- **`/recall -D` searches the archive AND the live buffer**, archive half first, cut at `wseq < (oldest live line's archive_seq)` so the overlap (every live line was archived as it arrived) isn't listed twice. The two halves are then **disjoint by construction**, which is why nothing de-duplicates at the seam — the old `ts_ms` cut could not make that guarantee, because equal timestamps straddled it in both directions. Page Up (`load_before_wseq`) cuts the same way and stamps the real `wseq` onto the prepended lines, so a Page Up followed by a `/recall -D` does not list the same text twice. A timestamp fallback is kept permanently for a pre-migration archive, a buffer predating archiving, or a degraded allocator. A result block is therefore mixed, and provenance is per match: `execute_recall_with_source` carries each match's `OutputLine::archive_sourced` out, and `emit_recall` emits one homogeneous block per contiguous run rather than widening `ServerData` with a parallel per-line array (matches come out in buffer order, so there are at most two runs). Typed input is never archived — `log_input_enabled` writes it to the per-world log *file* only — so `-D -i` reaches it purely through the live half.
- **`strip_mud_tag` must run BEFORE any display prefix is added** (`process_output_line`, and `renderOutput`/`appendNewLine` in app.js). It only fires on a line starting with `[`, so prefixing first silently suppresses it — which is how `/recall` output came to keep MUD tags that the same line shows stripped when it arrives live. With `-D` merging both sources, one result block can hold the same MUD line from the archive (🛢️) and from memory (✨); if the prefix gates the strip, those two render differently.
- **`from_archive` and `archive_sourced` both mean "this text came from scrollback.db", but only `from_archive` means "never deliver it".** `from_archive` marks locally-prepended Page Up scrollback: fabricated seqs, filtered out of every delivery path (`push_deliverable_lines`, the world-switch seeding, `claim_unviewed_lines`, the ScrollbackLines ranges). `archive_sourced` marks a `/recall -D` result — archived text emitted as an ordinary, seq-carrying, broadcast line — and is display-only. Display code must ask `OutputLine::shows_archive_prefix()`, never either flag alone, or the two render differently. Setting `from_archive` on a `/recall -D` line would make it vanish from every remote client *and* trip the Phase F ledger audit; folding `archive_sourced` into `from_archive` on the wire would be worse still — app.js's `bufferIsCorrupted()` reads any wire `from_archive` as proof of a pre-1.5.23 server and throws the client's whole buffer away. On the wire it is per-line on `TimestampedLine` and batch-level on `ServerData` (a recall block is homogeneous; `broadcast_output_range` derives it with `all`, never `any`, so a mixed batch can't put 🛢️ on ordinary client lines).
- **Every line added to `World::output_lines` must be broadcast** (PROTOCOL-ROADMAP.md Phase E). `App::add_output`/`add_output_to_world`/`emit_client_lines`/`process_server_data` all do; a raw `output_lines.push(...)` or a bare `push_line_respecting_pending(...)` does **not** — the TUI renders it and no client ever sees it, and the consumed `seq` leaves a permanent hole in every client's delivered-range tracking. Use `App::push_and_broadcast_line` (push + broadcast iff it landed in `output_lines`, `end_seq: Some(seq)` always). A site inside `for world in &mut app.worlds` can't broadcast from there — collect and emit after the borrow ends. Six such sites existed, each duplicated 2-3x across the console/headless/daemon loops, which is precisely why they drifted; prefer one shared helper over patching a copy. Related: a broadcast carrying `seq: 0` for a line that *was* stored with a real seq is the same class of bug — the line arrives but its seq is never recorded, so the ack audit sees a permanent gap.
- **The server audits itself against a broadcast ledger** (PROTOCOL-ROADMAP.md Phase F). `World::broadcast_ledger` records every seq actually put on the wire (same coalesced-range algorithm as `app.js`'s `_seenRanges`, fed from `App::note_broadcast` in the two fan-out helpers — `ws_broadcast`/`ws_broadcast_to_world`, deliberately NOT `ws_send_to_client`, since a single-recipient send is not delivery to everyone). `App::audit_broadcast_ledger` runs on every `PongCheck` and enforces the one invariant this whole bug class violates: **every line in `output_lines` below `pending_floor_seq()` must have been broadcast.** A violation is logged as `SEQ-LEDGER` (with the line's text) and re-broadcast, so a *new* leaking path self-heals and identifies itself instead of costing another user report — six paths have been fixed one at a time already. `/dump` prints the ledger per world; one range spanning `(0, next_seq-1)` is healthy, more than one is the signature. Not a violation: pending-held lines, the newest line (a broadcast may be in flight), an outstanding partial. When you add a `ServerData` site with a real seq, `end_seq` must be `Some(..)` — a bare `seq` reads as "not a real seq" on the client whenever it is 0.
- **A client that can't fill a gap must give up on it, not retry forever.** `requestGapFill()` anchors on `contiguousFrontier()`, so a seq the server can no longer produce (Ctrl+L's selective flush and a splash clear remove lines from `output_lines`; the archive prepend caps it at 10k) freezes that anchor: every reply re-delivers only what the client already has, `backfill_complete` stays false, and the `ScrollbackLines` handler re-requests the identical range without bound. `closeOldestSeqHole()` after 2 no-progress replies is the only terminating outcome; the loss is reported via `ReportGap` → `SEQ-HOLE` in `remote.log` rather than silently absorbed. Similarly, `evaluate_ack_audit`'s stall suppression is time-bounded (`AUDIT_REFIRE_INTERVAL`), never permanent — the likeliest cause of a stall is a full outbound channel, which is also what drops the `ResyncRequired` meant to fix it.
- **Never write a C1 control (U+0080-U+009F) to the terminal.** A terminal in a UTF-8 locale decodes `C2 9F` back into U+009F = APC and swallows everything until a String Terminator — which is the cursor positioning, scroll-region reset and separator-bar/input-area draw `render_output_crossterm` queues right after the line. U+009B (CSI) and U+0084 (IND, scrolls) are destructive too, and tmux is stricter than a bare xterm. The symptom is a mangled separator bar and input area plus stale text from another world left on screen, returning on every repaint of the offending line — Ctrl+L and `/reload` included, because the line is still in the buffer. It is invisible to Clay's own accounting as well: `unicode_width` reports `None` for a C1 char, so `visible_width` counts it as zero columns. The reachable path is ordinary MUD text: a world set to an 8-bit encoding while the MUD actually sends UTF-8 turns every emoji into a run of C1s. Guarded in two places — `Encoding::decode` (the `Latin1` arm decodes 0x80-0x9F as **Windows-1252**, not the strict ISO-8859-1 C1 block, and the control filters at the end drop any C1 the UTF-8 path lets through) and `rendering::expand_for_display` (`encoding::strip_c1_controls`, for text replayed out of scrollback.db that was archived before the decode guard existed). Strip at `expand_for_display`, never at the `Print` sites, or `visible_width`/`display_rows` measure a different string than the renderer emits. The decode half is shared by every interface; the display half is console-only on purpose — only a terminal interprets C1, a browser renders it as nothing.
- **The input area has exactly one display-line walk** (`InputArea::walk_line_starts`). Everything that maps a byte offset in `InputArea::buffer` onto a screen position goes through it or through `input::input_char_width`, which measures the `display_control_char` substitution the renderer actually draws rather than the raw character. `render_input` used to carry its own copy of the walk to find where its viewport started, and the two disagreed: on an empty line the renderer's version stepped over the newline with a `.max(1)` and then skipped the *following* newline as well, losing one display line per adjacent pair of blank lines. The drift accumulated down the buffer, so a large paste drew a region hundreds of lines from the cursor - reported as "the input pane doesn't show anything but spaces". A second walk is also how the input area gets slow: `cursor_line`/`cursor_column` are one pass (`cursor_line_col`), `line_starts` is gone in favour of `line_span`/`line_window_bytes`, which stop at the line asked for instead of building a `Vec` entry per display line, and `render_input` materialises only the slice inside the viewport rather than copying the whole buffer into a `Vec<char>` each frame. Spell-checking is scoped to that same window (`find_misspelled_words_in_window`, widened outward to whole words so an edge-cut word isn't judged as a fragment; `cached_misspelled` holds absolute **byte** offsets). A paste over `input_handler::MAX_INPUT_PASTE_BYTES` (64 KB) is refused with a message rather than truncated - a clipped paste in a command line is a command the user did not write. Bracketed paste must splice text in with one `insert_str`: the SSH remote console fed it through `insert_char` per character, and since every insert re-derived the cursor line by walking from the start of the buffer, an N-character paste was O(N^2).

- **TF's `%textdiv` divider exists only as the console draws it.** `App::track_console_world` (called from `ui()`, so the master console and the SSH console alike, however the switch happened) sets a world's `console_seen_seq` as the console leaves it and its `console_textdiv` as it arrives; `rendering::console_divider` decides where the divider goes, and its rows are spliced into the anchor line's rows by both renderers. While `%textdiv` is set, `Settings::nli_drawn()` (and app.js `nliDrawn()`) is false: TF's divider replaces Clay's ▶ markers.

- **Only the user un-pins the output view** (`app.js` `followBottom`). Whether the view follows live output is one explicit flag: set by reaching the bottom (any means) and by `scrollToBottom()`, cleared ONLY by a scroll that moved the view **up** within `USER_SCROLL_WINDOW_MS` of user scroll input (touch/wheel/pointer on the output, or a scroll action/PgUp/PgDn - `noteUserScrollIntent()`). Every "was the user at the bottom?" decision (ScrollbackLines branches, resize handlers, `withOutputScrollGuard`, `setFontSize`, `appendNewLine`'s tail, more-mode's pause, the render-window grow branch) reads `followBottom`, never raw `isAtBottom()`: that geometry is wrong for a following user whenever the Android IME shrinks the view, lines land between frames, a setting reflows the buffer, or - after a resume - every event queued in the background fires at once. Deriving the user's state from scroll events is what let a code-caused scroll pause more-mode and let the grow branch add 500 lines above the view: the "keyboard opens after resume and it jumps up hundreds of lines and stays there" report, three rounds of it. A `ResizeObserver` on the container and `#output` re-pins a following view after any layout change; a code-caused drift of a following view re-pins in the scroll handler and, if over 3 screens, reports `SCROLL-JUMP` (`recordClientEvent` → `CLIENT-LIFECYCLE` in `remote.log`, with the recent render/scroll causes). If you add a new user-driven way to scroll the output, call `noteUserScrollIntent()` in it, or scrolling up that way will be undone.
- **Kokoro TTS is loaded at runtime, never linked** (`src/kokoro.rs`). `TtsMode::Kokoro` runs Kokoro-82M through the sherpa-onnx C API, which `/tts install` downloads (runtime for this platform + the model build `kokoro::preferred_model` picks for the CPU: int8 `kokoro-int8-multi-lang-v1_0` where 8-bit matmul has a fast path (x86 AVX-512 VNNI, ARM), else the full `kokoro-multi-lang-v1_0` - on AVX2-only x86 the int8 build is ~4x SLOWER (0.95 s vs 0.26 s for a 1 s sentence on a 5600X; slower than real time on an i5-8400T), `install_in` accepts either and `/tts install` replaces the wrong one; the worker reloads a session whose model directory is no longer the install's, and the switch leaves the old build's directory in place until `kokoro::remove_stale_build` at the next start, because sherpa-onnx initialises espeak-ng ONCE per process with the first model's `espeak-ng-data`: delete that directory under a loaded session and every later line is a 0.2 s blip, reload or not) into `~/.clay/tts` (`CLAY_TTS_DIR` overrides) and `libloading` opens on the first utterance - so the binaries stay the size they are, no build machine needs the libraries, and every build has the mode (the static musl console reports that it cannot load a shared library; `/tts install` and `kokoro::build_can_load` say so). The `repr(C)` config structs mirror **one** header version (`kokoro::RUNTIME_VERSION`, pinned by `ffi_struct_sizes_match_the_header`); a newer runtime means re-reading `c-api.h`, never just bumping the constant, and `install_in` refuses a runtime at another version. The engine is one worker thread: the model (~1 s) is loaded **ahead** - `Engine::warm` via `App::warm_kokoro` at every single-user startup, on a settings save that leaves Kokoro selected (`note_kokoro_selected`), after `/tts install` and `/tts voice`; the attached native GUI's `warm_kokoro_if_wanted` does the same for its own copy - on every CPU up to eight (`num_threads`), then `SherpaOnnxOfflineTtsGenerateWithConfig` with `max_num_sentences = 1` so the callback streams each sentence into rodio before the next is synthesized (debug.log: "first audio after"), and "latest wins" like the Local engine (a generation counter the callback checks; `tts::stop`/F9 bump it, a warm-up does not). **Idle, the engine must cost nothing**: the audio stream is opened by the first line (never by a warm-up) and closed after `OUTPUT_LINGER` (30 s) of silence - an open rodio stream wakes forty times a second to hand the sound server silence, which it mixes the whole time ("clay is consistently using 10% of cpu and should be idle") - and a settings save that leaves Kokoro, or `/tts remove`, sends `Job::Release` (`tts::release_kokoro` from `App::note_kokoro_selected`; the attached GUI's `warm_kokoro_if_wanted` does the same for its copy): the model (hundreds of MB, the runtime's threads) and the stream go, the library and the idle worker stay, and the next warm-up starts over. Before this the engine outlived the setting: turning TTS off changed nothing. Until the files are installed, Kokoro mode speaks with the Local engine - **never silently**: `tts::speak` returns true for that fallback, `App::speak_text`/`note_kokoro_missing` say so once (and `note_kokoro_selected` at the moment the setting is chosen), and the native GUI attached to another Clay says its own line (`ClayView::KOKORO_MISSING_HERE`), because the voice plays on *its* machine with *its* files - so there `/tts status|install|remove|test` are handled by the GUI itself (`ClayView::tts_command`), only `voices`/`voice` (the shared setting) go to the server. The voice (`Settings::tts_voice`, `kokoro::VOICES`) rides `GlobalSettingsMsg`/`UpdateGlobalSettings` as a string, empty = unchanged/old peer. `CLAY_TTS_WAV_OUT=<file>` writes the audio instead of playing it (tests, headless boxes). Kokoro's waveforms peak at 0.25-0.4 of full scale where espeak and Piper sit near 0.9 ("turned the volume up and can still barely hear it"), so `Sink::push` lifts every sentence by `OUTPUT_GAIN` (2.5), peak-limited to `PEAK_CEILING` - one gain per sentence, never a clip. **Audio opens through `audio::open_output_stream`, never `OutputStream::try_default` directly**: on Linux it prefers the `pipewire`/`pulse` ALSA device over `default`, because on a PipeWire desktop without `pipewire-alsa` `default` is the sound card itself - Clay then played outside the desktop's mixer, no volume control reached it, and Kokoro was "barely audible" next to espeak (which talks to the server) - and the MUD's sounds and the voice must share the same choice. sherpa-onnx reports with `fprintf(stderr)`, which the console cannot survive: `platform::StderrToLog` sends fd 2 to debug.log for the duration of each library call and of the device probe (unix), and `voice_lexicons` hands it ONE English lexicon per voice (GB for `b*`, US otherwise) plus Chinese - both English lexicons at once made it print "Duplicated word ... Ignore it." for every GB entry onto the screen.
- **`/update` is one command that updates what can be updated, one program at a time** (`src/selfupdate.rs`). The server's half runs through `App::start_server_update`/`finish_server_update` (console, GUI master, `-D` daemon; multiuser refuses) and answers a remote requester with `WsMessage::UpdateOutcome` before the `ServerReloading`; the client's own half (native core `start_update` → `Effect::SelfUpdate`, app.js `updateFlow` → `proceedOwnUpdate`, the SSH console's `update_flow`/`pending_update`) starts only after that answer - and after the next `InitialState` when the server reloaded - because the two can be the **same file** on the same machine, and two concurrent installs would write the same staging file; `selfupdate::exe_replaced()` then skips the download and just restarts. ### Connection Security

Incoming connections are gated in `src/http.rs` before anything is served. Design record: `SECURITY-ROADMAP.md`; user-facing summary: `SECURITY-NOTES.md`.

- **Stealth path (`web_path` setting, default `"clay"`)**: web UI served only under `/clay/...`. Any other path from a non-localhost client is silently dropped (connection closed, zero response bytes) and records a ban strike — except `/favicon.ico` and `/apple-touch-icon*`, which drop without a strike. Empty `web_path` = legacy mode (UI at `/`, 404s as before). Localhost always works at both `/` and `/clay/` (the GUI WebView depends on this). Routing decisions live in the pure `decide_route()`; `SecurityGate` carries the shared allow-list/auth-key/ban-list state into all three server variants.
- **Accept-time IP gate** (`gate_connection()`): when `websocket_allow_list` is non-empty, non-listed non-localhost IPs are dropped *before* the TLS peek — no handshake, no certificate, no redirect (`GATE-DROP`, deliberately not a ban strike, or the knock below could never get through). Allow-list membership never skips authentication.
- **CLAY-KNOCK v1**: in-band auth-key preamble on the same TCP connection, before TLS/HTTP. Client sends `C7 4C 41 59 01 00`; server replies `C7 4B` + 32 random bytes; client sends raw `SHA256(auth_key || challenge)`; server acks `C7 06`. First byte `0xC7` disambiguates from TLS (`0x16`) and HTTP (ASCII) in the existing first-byte peek. A knocked connection may **WebSocket-upgrade at any path but never fetch a page** (`KNOCK-HTTP-DENIED`), and still performs normal WS auth. Android implements it in `NativeWebSocket.java` (`KnockSocketFactory`/`KnockSocket`, with fallback for old servers). Multiuser has no auth key → knocks always fail there.
- **WS auth matrix**: no allow list → password or auth key from anywhere; allow list set → password only from listed/localhost/whitelisted addresses, everyone else must knock with the auth key.
- **Ban exemption (D6)**: once an allow list is configured, the accept-time gate already drops every non-listed IP before it can reach any probe-strike site — so a probe strike can only ever ban a *legitimate, allow-listed* caller, never a scanner. `SecurityGate::strike()` is the one chokepoint every probe-strike site calls; it never bans an IP that's localhost, runtime-whitelisted, or matches a *specific* allow-list entry (exact IP, IP wildcard, or hostname pattern). A bare `*` allow-list entry does **not** confer this exemption — `*` means "let everyone reach the UI," not "nobody can ever be banned." `redirect_http_to_https()` (the plain-HTTP-on-the-HTTPS-port handler) reuses `decide_route()` directly instead of a separate reachability check, so it can never drift out of sync with it again — that drift was the root cause of a bug where an allow-listed user typing `http://` instead of `https://` got banned after two tries. Failed WebSocket password auth is the one exception: it still bans, and still applies to allow-listed IPs, via `BanList::record_auth_failure()` (threshold 5, not 2 — see `SECURITY-ROADMAP.md` D6). A connection that already knocked skips the "not in allow list" WS strike too (it proved a valid key; banning it would lock it out of its own recovery path).
- **Debugging**: `~/.clay/remote.log` records `HTTP-DROP`, `GATE-DROP`, `GATE-TIMEOUT`, `TLS-ON-PLAIN` (ClientHello on a plain-HTTP server — logged, never struck), `KNOCK-OK`/`KNOCK-FAIL`/`KNOCK-BAD-MAGIC`, `KNOCK-HTTP-DENIED`, `WS-PATH-DROP` alongside the existing `BANNED`/`CONN-LIMIT`/`TLS-*` events. A silent drop is intentional — expect zero bytes, not an error page. `log_remote_event()` is a no-op under `#[cfg(test)]` — tests must never append to a real user's `~/.clay/remote.log`.
  Output-sync diagnostics land in the same file: `SEQ-LEDGER` (a stored line the server never broadcast — always a bug, always names the line), `SEQ-HOLE` (a client gave up on a seq range it was never sent), `SEQ-AUDIT` (a client's ack vs. what it is owed; transitions always, steady states only under debug), plus the client-reported `SEQ-MISMATCH`/`DUPLICATE`/`OUT-OF-ORDER`. On a healthy instance none of these appear; any of them is the "the TUI shows a line the phone doesn't" class, and `/dump`'s per-world `broadcast_ledger` line localizes it. `SCROLL-JUMP` (a `CLIENT-LIFECYCLE` event from Android: code moved a view that was following live output more than 3 screens away; details include the recent render/scroll causes) is the signature of the keyboard/resume jump class. `WS-BAD-MESSAGE` (`type=.. err=.. len=..`) fires at the three sites that deserialize a raw `WsMessage` off the wire — the server's main WebSocket receive loop and both of the SSH remote console's receive sites (the InitialState wait loop and the main loop) — whenever a message fails to deserialize; this is the amplifier for every wire-shape bug (e.g. a missing `#[serde(default)]` on an `Option` field), so a message that used to vanish silently now names its `type` (best-effort, via a raw JSON probe) and the serde error.

**The Clay password never crosses a network in the clear.** Invariants, all enforced in code: (1) `GlobalSettingsMsg.ws_password` is always sent empty — clients get only `ws_password_set` — and `UpdateGlobalSettings.ws_password` empty means *unchanged*, never "clear" (a client that was never sent the password echoes `""` on every unrelated save; clearing is console-only). (2) A bare password hash or raw auth key (`challenge_response: false`) is accepted only from loopback (`websocket::plain_credential_allowed`) — it replays; clients answer only a ServerHello challenge and send nothing if it is missing (app.js `authenticate`/`tryAuthWithKey`, the three editor pages' `doAuth`). The one bare-hash sender is `AUTO_PASSWORD`, which only ever targets 127.0.0.1. (3) Plaintext `ws://` is used only to a loopback host (`util::is_loopback_host`; app.js `isLoopbackHost` in `buildCandidates`; the remote console/grep/import clients and `run_remote_webgui` refuse to fall back for a remote host). (4) A spawned GUI window inherits the parent's login in-process only (`InheritedAuth` → injected `INHERITED_AUTH`, or a same-origin `window.opener.__clayInheritAuth()`), never via a URL.

**Outbound TLS is pinned, not CA-verified (D7).** Every client-side TLS connection (MUD worlds, remote-console, WebView proxy, hot-reload proxy, `/connect`) uses `platform::danger_rustls::TofuVerifier` (rustls) or `platform::check_native_tls_peer_pin` (native-tls), not CA verification — Clay's own server and most MUDs are self-signed. Trust-on-first-use: pin `sha256(end_entity_DER)` in `~/.clay/known_hosts.dat` (`persistence::add_pin`/`get_pin`/`replace_pin`) silently on first sight; on a mismatch, **block** and surface old-vs-new fingerprint + a "trust new cert" action in all three UIs (`WsMessage::CertMismatch`/`TrustCertificate`, web `showCertMismatchDialog`, TUI `create_cert_mismatch_dialog`). **The signature-verification methods MUST do real verification** (delegate to `rustls::crypto`) — pinning the fingerprint alone is defeatable by replaying the public cert without its key. See `SECURITY-ROADMAP.md` D7.

**Other D7 invariants**: secret files go through `util::write_secret_file`/`secure_create_file`/`secure_append_file` (0600; `~/.clay` is 0700) — never plain `File::create` for anything holding a password/key/token. Static-secret comparisons use `util::constant_time_eq`. Multiuser handlers taking a client `world_index` must check `world.owner == username` (see `ConnectWorld`/`SwitchWorld` in `daemon.rs`). MUD text reaching the web client must be escaped — `app.js` `escapeHtml` (incl. quotes) + `sanitizeHtml` on output sinks, and any HTML-building helper (e.g. `convertDiscordEmojis`) must escape what it interpolates. GMCP media URLs are http/https-only with internal targets refused.

**The web server is always TLS-capable for remote clients; localhost is always plain (D8).** The single-user `/web` popup no longer has a Protocol setting — `web_secure` is kept in `Settings`/`GlobalSettingsMsg`/settings.dat only for wire/import compat, never read to choose HTTP vs HTTPS. `resolve_web_cert_files()` (main.rs) picks a user-provided cert (`websocket_cert_file`/`websocket_key_file` — "Custom Cert File: Yes" in the popup) if set, else an auto-generated self-signed cert whose PEM now lives in `Settings.web_cert_pem`/`web_key_pem` (public cert base64'd cleartext, private key base64'd-then-`secret()`-encrypted — same at-rest mechanism as `websocket_auth_key`), materialized to `~/.clay/cert.pem`/`key.pem` as a derived on-disk cache. In the TLS accept loop (`http.rs`, both native-tls and rustls variants), the existing first-byte-peek branch that used to redirect any non-TLS request to HTTPS now instead serves a **loopback** connection plain via `route_connection` (no handshake) — remote non-TLS requests still redirect. This is why the GUI WebView (`ws://127.0.0.1`) never sees a cert prompt while remote clients always get TLS. Auto-approval on the Clay↔Clay path needs no new work — the existing D7 `TofuVerifier` pinning already silently trusts on first connect and only blocks+prompts on a later mismatch, for every outbound Clay client (remote console, WebView proxy, Android). `-D` and `--multiuser` (`daemon.rs`) use the same always-TLS server now (their old plain-HTTP mode sent every login and settings message across the network in cleartext); `--multiuser` resolves its cert via `resolve_web_cert_files_multiuser`, which never saves — saving would write multiuser.dat's settings over this machine's settings.dat. `--local-server` binds `start_https_server` to 127.0.0.1 via `http_bind_host()`. Auth Key is read-only in `/web`/web-settings now; Copy/Regen/Delete live in a "Modify Key" sub-popup (TUI: `popup/definitions/modify_key.rs`; web/GUI: `showModifyKeyDialog` in `app.js`), with Regen/Delete reusing `App::handle_ws_key_request`/`handle_ws_key_revoke` (immediate effect, broadcast to all clients) rather than waiting on the popup's own Save. See `SECURITY-ROADMAP.md` D8.

### TinyFugue Compatibility

Clay's TinyFugue (TF) compatibility layer (`src/tf/`) and its keybinding grammar
(`src/keynames.rs`, `src/chords.rs`, `src/keybindings.rs`) are specced against real TF
5.0 in `TINYFUGUE-COMPAT.md` (design record — per-key and per-command ruling tables,
changed defaults, intentional differences) and `docs/markdown/06-tf-commands.md` /
`docs/markdown/07-keyboard-shortcuts.md` (user-facing).

- **Script-test suite**: `tests/tf/cases/*.tf` + `.expected`, run via `cargo test
  tf_script` (harness: `src/tf/script_tests.rs`). Add a fixture by writing the `.tf`
  file, then run `tools/tf-oracle.sh --write <name>.tf` to generate its `.expected`
  from real `tf` (needs `tf` on `PATH` — `apt install tf5`) — never hand-write an
  `.expected` file. A case needing the real TF library starts with `;; requires-lib`
  and is skipped (not failed) when `$TFLIBDIR`/`/usr/share/tf5/tf-lib` isn't found.
- **The xfail ledger** (`tests/tf/xfail.txt`, format `case-name | substring-of-failure`):
  a known-failing case is listed here, not silently left red. A listed case that
  starts passing is itself a test failure ("remove it from xfail.txt") — that's the
  signal a fix landed. Never add an entry to make a red test green without a real,
  understood gap behind it.
- **Key-name grammar and dispatch order**: every key name (`keybindings.dat`, `/bind`,
  a live keypress, the web keybind editor) is canonicalized through
  `crate::keynames::parse_key_name`/`KeySeq::canonical` — this is the one place chords
  (`^X^R`), TF's raw spellings (`^[b`, `\033`), and case-significant `Esc-` forms
  (`Esc-j` != `Esc-J`) are understood. A pressed key resolves in this order, identical
  on console and web/GUI/SSH-console clients: (1) a `/bind`/`/def -b`/`-B` match, (2) a
  `key_<name>` macro, (3) the built-in action table (`ACTIONS`/`dispatch_action`), (4)
  literal character input.
- **Three-UI rule for a new action id**: adding to `ACTIONS` in `src/keybindings.rs`
  is not enough on its own — `dispatch_action` (console), `dispatchActionImpl` in
  `app.js` (web/GUI), `dispatch_remote_action` in `src/remote_client.rs` (the SSH
  remote console keeps its **own** copy of the dispatcher, so this is a fourth site,
  not covered by the other three — an action missing here does nothing at all when the
  key is pressed over SSH), and the keybind editor's action list (it reads
  `actions_json`, but a new category string also needs adding to its own `order` array
  or the whole category is silently hidden) all need the new id, or an interface
  silently can't run it. `RunKeyBinding{key, kbnum}` is the wire message a remote client sends back to the
  server when a keypress matches a TF `/bind` entry the server told it about
  (`tf_bound_keys_json`/`GlobalSettingsMsg`) — TF `/bind` state lives only in the
  server's own `TfEngine`, so a remote client can't run one locally.
- **The engine records, the App applies.** A TF command's output, sends, Clay commands,
  world definitions, connects, shell escapes and the rest are ordered `TfEffect`s
  (`src/tf/effects.rs`) collected per command frame; the App applies them through
  `src/tfrun.rs` (`run_tf_effects_console`/`_client`/`_daemon`, and
  `apply_tf_effects_now` + `deferred_tf` for synchronous callers such as hooks and
  triggers). New App code should run TF through those, not act on a
  `tf_engine.execute` result itself, or it drops everything but the result. A special
  variable bound to a Clay setting (`special_vars::BOUND`: more, wrapspace, isize,
  insert) emits `TfEffect::Setting(name, value)` - the value must travel with
  the effect, because `sync_tf_world_info` re-mirrors Clay's settings into those
  variables and would otherwise overwrite the new value before the effect is applied
  (an rc's `/addworld` before a later `/set` of one did exactly that). Clay has no
  non-visual mode (user ruling): `%visual` always reads `on`, and `/visual off` is
  refused (`special_vars::NO_NONVISUAL_MODE`).
- **TinyFugue startup** (`src/tfstartup.rs`): TF's own command line (`clay mymud`,
  `-f`, `-c`, `-L`, `-n`/`-l`/`-q`) and the first of `~/.tfrc`, `~/tfrc`, `./.tfrc`,
  `./tfrc`, run once at a cold start - never on a reload or crash restart, which carry
  the whole TF state over instead (`src/tf/snapshot.rs`, `tf_state=` in the reload
  file). The user ruled `-v` stays "version" and nothing auto-connects to the first world.
- **Tests never touch the real `~/.clay`**: under `cfg(test)` `get_home_dir()` is a
  per-process temp home and the engine's `HOME` points there too. A test that needs
  a file writes it under that home or `std::env::temp_dir()`. A test that needs a port
  for a server to bind takes `testserver::free_port()` - never "bind port 0, read it,
  drop it, bind again": the kernel can hand that same ephemeral port to another test in
  between, which is how "Address in use" failures came and went at random.
- **TF's status line** (`src/tf/status.rs`) replaces Clay's separator bar - in the
  console, web/GUI/Android (`#tf-status`, `layoutTfStatusRow` in app.js, a port of
  `status::layout_row`) and the SSH console - only once a script changes it
  (`StatusLayout::customized`); `App::refresh_tf_status` evaluates every world's view
  and sends `WsMessage::TfStatus` on change. Keep the Rust and JS layouts identical.
- **Two traps found the hard way**: `%;` (TF's command separator) is **not**
  quote-aware — a naive quote-aware splitter looks more correct but is wrong; real TF
  splits on every `%;` regardless of surrounding quotes. And TinyFugue does **not**
  expand `%var`/`$[...]`/`$(...)` on a bare top-level line read from a file — only
  inside a macro body, or via `/eval`'s own substitution pass; a script-test probe
  that needs expansion must be wrapped in a macro or `/eval`, and any engine change
  that substitutes a top-level file line unconditionally is reintroducing this bug.
