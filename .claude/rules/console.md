# Console and SSH console rendering and input

Design record for the console renderer, C1 controls, the input area's one display-line walk, sent lines, TF's %textdiv, the SSH console's reconnect. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08.

- **The SSH/remote console reconnects** (`run_console_client`): after `ServerReloading` or any drop it keeps the TUI, input and editor, and logs in again on a task (`reconnect_once`: `ConnectTarget::open` - the SSH session gets a new channel - then ServerHello, `AuthRequest` answering the new challenge with the kept password **hash**, then `InitialState` through `apply_initial_state`, which re-finds an open editor's world by name). A refused login or a changed certificate stops the retries with a message; a certificate is never trusted without the first connect's y/N prompt. While disconnected, `ws_tx` is a channel the loop drains to report typed lines as not sent.
- **Console rendering**: `render_output_crossterm()` bypasses ratatui for output area (raw crossterm for ANSI fidelity). Popups use ratatui. **Wherever ANSI text has to become ratatui spans** (TF's status row, the output drawn behind a popup/editor/splash, the input prompt) use `rendering::ansi_line(text, base)`, never a crate: ansi-to-tui 4 dropped every SGR sequence with two or more parameters whole (`ESC[96;44m` applied nothing while `ESC[44m` alone worked, so TF's `status_attr=Cbrightcyan,Cbgblue` showed no colour and a MUD's `ESC[1;31m` lost both behind a popup - found 2026-10-28, the crate is gone) and turned a reset into `Color::Reset`, which overrode the Paragraph's base style and lost the Web look's bar colour after a field with its own attributes. `ansi_line`'s reset, `39` and `49` go back to the caller's base.
- **A line of nothing but escape codes is drawn or hidden by one rule, in every interface**: `encoding::is_ansi_only_line` - escape codes and spaces only, with at least one escape, is hidden for good (F2 or not) **unless one of them sets a background colour** (`has_background_color`: 40-47, 100-107, a `48` parameter), which makes the line a blank row. The console draws by it (`process_output_line`, `search_line_visible`) and the server counts more-mode rows by it (`display_rows`); the native GUI calls it (`native_gui::core::client::hidden_line` → `Line::is_hidden`, which also feeds its more-mode row count), and app.js `isFillerLine`/`hasBackgroundColor` are its step-for-step port (`lineIsDrawn`, `lineRows` and the live `ServerData` path all ask it), pinned by `app_js_hides_the_lines_the_console_hides`. Before 2026-11-11 the two GUIs had a rule of their own - "escape codes only" with no background exception - so on The Chatting Zone, whose blank lines are `ESC[0;36m ESC[1m ESC[0;37m ESC[40m`, the GUI and the web page showed a `look` with none of its blank lines while the console and plain telnet showed them, and since the server counts rows as the console draws them, it held the look's last blank line for a "More 1" that Tab released as nothing (user report, with a `/dump` showing the one pending line; user ruling the same day: the GUIs show what telnet and the console show - a blank line on the console is a blank line in the GUI and the web interface). Checked by running the shipped app.js functions in headless Firefox against the Rust ones on 40,000 generated strings. Still different from telnet, on every interface alike, and to stay so (user ruling 2026-11-11: "the difference between an input window and single area"): a line of colour codes with **no** background stays hidden (TCZ's `ESC[0;36m ESC[1m`, the first line of every `look`'s reply) - telnet shows a blank row there, between the typed command and the room's name. Two more rulings from the same report, both "leave it": **every connected session sizes more-mode's page, paused or backgrounded** ("paused sessions are still being rendered", then "anything that is currently considered being live/active. A backgrounded phone connection may technically not be live but until that connection is disconnected, it should be treated as live": `viewer_output_dims` asks `console_shows`, never `console_watching`, and `min_viewer_lines`/`min_viewer_width` filter on `disconnected_at` alone, never `paused` or `visible` - the console's 21 rows paged the look for a 31-row GUI that had typed `/pause`), and **a blank line triggers More and is held like a line of text** ("a blank line is still a blank line"), even when it is the only thing left behind the pause. A new place that decides whether a stored line is drawn asks this rule, never a regex of its own.
- **Never write a C1 control (U+0080-U+009F) to the terminal.** A terminal in a UTF-8 locale decodes `C2 9F` back into U+009F = APC and swallows everything until a String Terminator — which is the cursor positioning, scroll-region reset and separator-bar/input-area draw `render_output_crossterm` queues right after the line. U+009B (CSI) and U+0084 (IND, scrolls) are destructive too, and tmux is stricter than a bare xterm. The symptom is a mangled separator bar and input area plus stale text from another world left on screen, returning on every repaint of the offending line — Ctrl+L and `/reload` included, because the line is still in the buffer. It is invisible to Clay's own accounting as well: `unicode_width` reports `None` for a C1 char, so `visible_width` counts it as zero columns. The reachable path is ordinary MUD text: a world set to an 8-bit encoding while the MUD actually sends UTF-8 turns every emoji into a run of C1s. Guarded in two places — `Encoding::decode` (the `Latin1` arm decodes 0x80-0x9F as **Windows-1252**, not the strict ISO-8859-1 C1 block, and the control filters at the end drop any C1 the UTF-8 path lets through) and `rendering::expand_for_display` (`encoding::strip_c1_controls`, for text replayed out of scrollback.db that was archived before the decode guard existed). Strip at `expand_for_display`, never at the `Print` sites, or `visible_width`/`display_rows` measure a different string than the renderer emits. The decode half is shared by every interface; the display half is console-only on purpose — only a terminal interprets C1, a browser renders it as nothing.
- **The input area has exactly one display-line walk** (`InputArea::walk_line_starts`). Everything that maps a byte offset in `InputArea::buffer` onto a screen position goes through it or through `input::input_char_width`, which measures the `display_control_char` substitution the renderer actually draws rather than the raw character. `render_input` used to carry its own copy of the walk to find where its viewport started, and the two disagreed: on an empty line the renderer's version stepped over the newline with a `.max(1)` and then skipped the *following* newline as well, losing one display line per adjacent pair of blank lines. The drift accumulated down the buffer, so a large paste drew a region hundreds of lines from the cursor - reported as "the input pane doesn't show anything but spaces". A second walk is also how the input area gets slow: `cursor_line`/`cursor_column` are one pass (`cursor_line_col`), `line_starts` is gone in favour of `line_span`/`line_window_bytes`, which stop at the line asked for instead of building a `Vec` entry per display line, and `render_input` materialises only the slice inside the viewport rather than copying the whole buffer into a `Vec<char>` each frame. Spell-checking is scoped to that same window (`find_misspelled_words_in_window`, widened outward to whole words so an edge-cut word isn't judged as a fragment; `cached_misspelled` holds absolute **byte** offsets). A paste over `input_handler::MAX_INPUT_PASTE_BYTES` (64 KB) is refused with a message rather than truncated - a clipped paste in a command line is a command the user did not write. Bracketed paste must splice text in with one `insert_str`: the SSH remote console fed it through `insert_char` per character, and since every insert re-derived the cursor line by walking from the start of the buffer, an N-character paste was O(N^2).
- **Lines sent stay in the input area (TF's `%cleardone` off, `Settings::clear_input_on_send` false, the default).** Display state per viewer, never on the wire (only the setting is): the console's and the SSH console's `InputArea::sent`/`sent_rows` (filled by `App::take_input_line`, the one Enter path for the console key, `/dokey NEWLINE` and the SSH key), each native window's `InputState::sent` (`ClayView::send_line` wraps the real `send_line_now`), app.js `#input-sent` (`sendCommand` wraps `sendCommandLine`). A sent line keeps its text alone, never the prompt it was typed after (TF does keep it; user ruling 2026-10-24: the prompt belongs to the line being typed, which shows the current world's, so a world switch changes nothing above it); a masked line is an empty row (the password is never stored). The sent lines survive a hot reload: the console's reload state carries them (`input_sent=`, `input_sent_rows=`), and the GUIs stash their input area for a relaunch - the native GUI in the window prefs (`stash_input_for_relaunch`/`restore_input_after_relaunch`, surfaces.rs), the WebView page in `localStorage` (`stashInputForRelaunch`) - taken back only within two minutes (user ruling 2026-10-24: every interface keeps it). Rows the typed line takes are gone for good, as in TF (`InputArea::fit_sent`, native `fit_sent`, app.js `layoutInputArea`), and the input area's height never changes on Enter. Phones always clear (`deviceMode === 'phone'`, user ruling); Termux follows the setting. The `redraw` action clears them in every interface, as TF's redraw clears its input window. Two traps: in the console the typed line's height is `input_height - sent_rows` (`rendering::input_rows_split`, `input.visible_height` after `fit_input_area`), never `input_height` - `render_input`, `render_input_area` and `queue_input_cursor` all draw or place the cursor in it; and in app.js the textarea's value is set in two dozen places, so a wrapper on the element's own `value` setter relayouts after each (`relayoutOnInputValueChange`) - set the value through `elements.input.value`, never the prototype's setter, or the sent rows don't make way.
- **TF's `%textdiv` divider exists only as the console draws it.** `App::track_console_world` (called from `ui()`, so the master console and the SSH console alike, however the switch happened) sets a world's `console_seen_seq` as the console leaves it and its `console_textdiv` as it arrives; `rendering::console_divider` decides where the divider goes, and its rows are spliced into the anchor line's rows by both renderers. Anything that pages the console must measure with `RowMetrics::for_console` (or `.with_divider(app.console_divider_rows())`), which counts those rows as the line's - a plain `RowMetrics::new` there would make Page Up skip or repeat a row at the divider. Budgets for output not yet drawn (more-mode) and other viewers' widths use `new`. app.js keeps its own seen marks (`clearLeavingWorldState`/`arriveTextdiv`), and the divider is not a `.line` element. While `%textdiv` is set, `Settings::nli_drawn()` (and app.js `nliDrawn()`) is false: TF's divider replaces Clay's ▶ markers.
