# Start-up, hot reload, GUI mode and self-update

Design record for how Clay starts, chooses an interface and a web port, hot-reloads, restarts after a crash, records its ending and updates itself. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08.

- **Hot reload**: `exec()` replaces process, TCP socket fds preserved via cleared FD_CLOEXEC. TLS connections need proxy process. The `CLAY_HTTP_LISTENER` env var / Windows listener-socket-handle-passing (`platform.rs`, `start_http_server`'s `inherited_handle` param) is now dormant for the GUI path — since D8 (see below) the GUI always uses the always-TLS-capable `start_https_server`, which doesn't wire it up, so Windows GUI reload relies on `start_https_server`'s existing bind-retry-with-backoff loop instead (same mechanism Unix always used). **That retry runs only for a successor whose predecessor held the port, or a restart** (`HttpsServer::bind_retry`: `http::port_released_by_predecessor(port)` at the start-up sites - `CLAY_RELOAD_WEB_PORT`, which `exec_reload`/`crash_restart` set from the listener the predecessor had via `platform::pass_web_port_to_successor` and *remove* when it had none, `*` for a crash with no App to ask; always on in `restart_http_server`, whose old listener goes when its accept task sees the shutdown), and only while the error is address-in-use; everything else binds once (`http::bind_listener`) and reports at once - a second Clay used to sit through all 10 x 300 ms on a blank screen before the console's first draw, and a `/reload` of it waited the same 2.7 s again (user reports 2026-10-28). A reload never forces the current world off its splash: `render_splash_centered` draws the output lines centred under the art, so "Reload successful" shows there; forcing the flag off (as both start-up paths did) left the splash `ensure_has_world` regenerates at column 0 after every reload. Every interface prints the failure through `http::start_warning` (`Warning: Failed to start HTTPS server [port in use]`, the user's wording); only the GUIs' "Clay failed to start" dialog (`GUI_HTTP_FAILED`) keeps `BindError`'s long form with the port's owner. That retry only works because the listener and accepted sockets are made non-inheritable (`platform::not_inherited`): Windows sockets, tokio's included, are inheritable by default, so the reload successor used to inherit the old listener, which then held the port it needed to bind. Every reload in v1.6.25's Windows GUI ended Clay that way. A GUI's successor is also spawned with null stdio + `CREATE_NO_WINDOW`: after `FreeConsole` the std handles are stale, and inheriting them could make the spawn fail. `webview_gui.rs`'s duplicate-instance probe detects a reload via the `--reload` arg (always present on a reload exec), not `CLAY_HTTP_LISTENER` — don't revert that or the probe false-positives "already running" and aborts the reload.
- **GUI mode**: The default wherever a window can be shown (user request 2026-10-29): a start naming none of `--gui`/`--web-gui`/`--console` opens the GUI when the build has one and `platform::gui_can_open()` - not over SSH (`SSH_CONNECTION`/`SSH_CLIENT`/`SSH_TTY`, every OS) and, on Linux/Termux, the display server GPUI would use is listening (WAYLAND_DISPLAY's socket when set - GPUI doesn't fall back to X11 - else DISPLAY's, in x11rb's order; a connect and no more, ~1 ms) - and the console otherwise; a named interface is never second-guessed. **A restart keeps the interface Clay is in** (user request 2026-10-29): every main Clay records it however chosen (`platform::note_running_ui`), and every restart names it in the reused command line (`platform::restart_args`: both `exec_reload`s, both `crash_restart`s, the WebView's software fallback; never `exec_with_args`, which serves attached GUIs and `/server`); the successor (main.rs, before the native-GUI block) keeps it unless it can't run there and the other can (`platform::restart_ui`: `display_can_open`, `console_can_run` = a foreground terminal), saying so after "Reload successful" (`restart_fallback_note`). A `--reload`/`--crash` naming no interface came from a Clay before this (v1.7.27 and older, the next `/update` included) and gets that version's default - GUI on macOS/Windows, console elsewhere - or the reloaded console came back as the GUI. **`/reload --console|--gui` switch it** (`Command::Reload { ui, bad }`, `platform::reload_options`; `App::reload_ui` carries it to `exec_reload`, since an MCCP2-deferred reload runs later from another loop): checked before anything is said or saved (`App::reload_switch_problem` → `platform::ui_switch_problem`: a GUI needs a build with one, a display, and the web port), because a successor that fails at start loses every connection; the main Clay switches only from its own window (`App::reload_switch_refusal`: handler A refuses every client, handler B all but `own_gui_client`); a GUI → console reload puts settings.dat's web password and `http_enabled` back (`App::drop_gui_web_override`), or the console would save the GUI's session password; on Windows the successor is started by what it will be (a console from a GUI gets `CREATE_NEW_CONSOLE` and takes the window's handles, `platform::take_new_console`). Attached clients switch themselves (`platform::attached_switch_args`: native GUI `reload_as`, the remote console's `relaunch_args`, the attached WebView's `reload:console` IPC); a browser or the phone app answers locally (app.js `RELOAD_SWITCH_ELSEWHERE`, pinned to main.rs's). `--gui` is the native GUI (`src/native_gui/`, `native-gui` feature, Rust >= 1.98; alone it runs Clay in-process via `native_gui::start_clay`, which mirrors `run_master_webgui`; `--gui=host` attaches) and is the platform default when built in; `--web-gui` is the WebView GUI, which `--gui` also opens in a build without `native-gui` (Termux); since 2026-11-16 the WebView GUI is built for Termux only, and a build with the native GUI and without it opens the native one for `--web-gui` (`platform::web_gui_to_native`, so the restart of a Clay that updated out of the WebView GUI keeps a window; `.claude/rules/build-features.md`). **A port already taken is not a refusal** (user request 2026-11-01, "running multiple clays should be supported"): the one start-up path for both loops, `start_web_server_at_startup`, takes the next free port above the configured one (`http::free_web_port`, probing `127.0.0.1` **and** `0.0.0.0` - Windows lets a loopback bind succeed beside a program listening on all interfaces), keeps it in `App::web_port_override` (never saved; cleared when the setting changes; `App::web_port` is what `/reach`, the router mapping and the GUIs' own window use, never the setting alone) and says so in the output with the port's owner and the attach address (`web_port_taken_notice`); `restart_http_server` keeps the port it holds and otherwise picks the same way. A reload or crash successor keeps the port its predecessor held (`http::predecessor_web_port`), so attached clients stay attached. The GUIs no longer probe the port themselves: they read `GUI_HTTP_PORT` once `GUI_HTTP_READY` is set. `-D` and `--multiuser` keep their configured port, being servers people connect to. A bind failed with address-in-use names the holder (`platform::port_owner`, netstat + tasklist on Windows; `http::bind_failure`), and `GUI_HTTP_FAILED` lets the GUIs' start-up waits report a server that couldn't start at once. **Quitting either GUI runs `/quit`'s cleanup in the Clay it carries** (`quit_in_process_clay` → the headless loop's `GUI_QUIT` arm → `App::quit_cleanup`, the same method the console's `/quit` uses: archive flushed, TLS proxies ended, UPnP mapping returned), bounded at 5 s, before the process ends; the native GUI then `process::exit`s as tao does for the WebView. Without it each TLS proxy took the GUI's going for a hot reload and lived a minute (the proxy waits 60 s for its client to come back), its MUD connection open - "takes forever for the exe to quit". A reload must never go through this path. The desktop release GUI assets carry the native GUI only (both until v1.7.36). The WebView master mode uses `run_master_webgui()` → `run_app_headless()`. `http_enabled=true`; the server is always TLS-capable (D8) but the WebView connects to `ws://127.0.0.1:<http_port>` (plain — localhost is always served unencrypted, see Connection Security below). **Both GUIs log their window in with the web password saved in settings.dat when there is one** (`gui_session_password` → `WsOverride::Saved`), so phones and browsers can log in with the one the user set in Settings > Web; only without one do they make a per-start random session password (`WsOverride::Session`), which `App::session_ws_password` keeps `write_settings_dat` from saving - it used to be made at every start regardless and saved, so the user's password was ignored at the next start and overwritten on disk, locking other devices out. Android's `--local-server` password is a session one too (the app keeps it in its prefs).
- **This machine's Preferred Interface and default server** (user request 2026-11-21: "allow the user to define a default server like the android app allows ... a Preferred Interface popup in the general page ... Only provide which options are available ... The server settings should be on a per host basis and not stored on the main instance. Any passwords or keys should be encrypted ... This should not override command line options"; rulings the same day: a bare `/server` opens the Server page and `/server host`, `--close`, `--cancel` stay; `--gui` and `--console` always start a standalone Clay; the two apply only when the command line names no interface). `src/clientconf.rs`: `~/.clay/client.dat` - `[client] preferred_interface`, `default_server`, `[server:host:port]` username/password/auth_key, the two secrets `persistence::encrypt_password`ed, written owner-only by `ClientConf::save` (skipped when unchanged); read and written only by the process running on that machine (the console, the SSH console, the native GUI's window, the WebView host through the `client-conf:` IPC and the injected `window.CLIENT_CONF`), never part of `Settings`, settings.dat, `GlobalSettingsMsg` or `UpdateGlobalSettings`. **Start-up** (main.rs, after the restart block, before `web_gui_to_native`): only with no `--console`/`--gui`/`--web-gui`, no `--reload`/`--crash`, no server/one-shot/`--ssh` mode and not a server build, `clientconf::resolve_start(conf, Can::at_start(), tf_given)` fills `console_arg`/`gui_arg`/`web_gui_arg` and everything after runs as for that flag; a TinyFugue world or option on the command line drops the default server (a local session). The interface: the preferred one if it can run (`Can::at_start`: a foreground terminal for the TUI, the build plus `gui_can_open` for the GUIs), else the first of GUI, Web GUI, TUI that can, else Clay's own default; with no preference, Clay's own default. **The desktop launcher runs a bare `clay`** (`desktop.rs`, `Exec=` without `--gui` since that day), so it reaches the default server and, having no terminal, never lands in the TUI. **A relaunch keeps a resolved attach**: `clientconf::note_resolved_attach` records `--gui=host` etc., and every attached relaunch site reads `clientconf::launch_args()` instead of `std::env::args()` (native `reload_as`/`relaunch`/`restart_now`, the remote console's `relaunch_args`/`relaunch_and_wait`, the attached WebView's reload). **Logins are per server** (`server_key` = lower-cased `host:port`, port 9000 by default): any attach with no other credential uses `login_for` - the native GUI in `native_gui::run` (below `CLAY_PASSWORD`/`CLAY_AUTH_KEY`, above native-gui.dat's own key), the console in `run_console_client` (sent at the ServerHello as `SavedLogin::auth_request`, the key's challenge answer first; a refusal falls back to the prompts, and `reconnect_once` reuses it), the attached WebView as `INHERITED_AUTH` with an `authKey` (app.js `seedInheritedAuth`). **The pages**: Preferred Interface is a select of `clientconf::offered()` (the TUI always; a GUI where built and `gui_can_open` in that session) showing `shown_preference`, saved through `save_preference` only when changed, so Settings over SSH (no GUI offered) never overwrites a GUI preference - console `/setup` `SETUP_FIELD_PREFERRED_INTERFACE` (`add_preferred_interface_field`, saved in `save_setup` by `save_preferred_interface`), native `SettingsView::preferred`, app.js `#setup-preferred-interface-row` (only with `CLIENT_CONF`). The Server page (Host, Port, Username, Password, Auth Key; blank Host = no default; `ServerPage::address`): console `popup/definitions/server.rs` (keys in `handle_new_popup_key`'s `is_server` block; opened by a bare `/server` in `commands.rs` and `run_remote_command`), native `windows/server.rs` `ServerForm` as Settings' `Tab::Server` and on its own as `Kind::Server` while there is no connection (`open_settings`), app.js the Clay Server tab with `.cs-desktop` hiding the app's `.cs-android-only` rows. **The WebView page is never given the saved password or key** (security review 2026-11-21, `.claude/rules/security.md`): `CLIENT_CONF.server` carries `hasPassword`/`hasAuthKey`, the two fields stay blank with "Saved - leave blank to keep", a typed value replaces, Forget drops, and the page sends the Server page (`server` non-null) only when its tab was opened in that Settings - a Save from General used to send a blank Host and clear the default server. `client.dat` itself: an `ENC:` value this machine can't decrypt is no secret (never sent as a literal password, which five refusals would turn into a ban), an address holds only address characters (`clientconf::valid_address`, on load and save), `Debug` output redacts both secrets. A bare `/server` in a browser says `clientconf::SERVER_PAGE_ELSEWHERE`; the Android app opens its own Clay Server tab, whose storage (SharedPreferences, unencrypted) is unchanged. The help text is `clientconf::SERVER_PAGE_HELP` (app.js `popupHelpTexts.server`, pinned). Judgment calls (reversible): the launcher change; the labels TUI/GUI/Web GUI; masked Password/Auth Key fields; no SSH fields on the desktop page; the TUI always offered in Settings.
- **Every Clay leaves a trace of how it ended in debug.log, whether Debug mode is on or not** (`src/crashlog.rs`, user request 2026-10-28: the GUI "closed without any warning a few times"). `crashlog::install()` is the first line of `main` for every mode: the one panic hook (`CRASH (pid N, thread T)`, a `CRASH CONTEXT` line from `crashlog::set_context` - the native GUI's world, view and indicator, each server loop's worlds at its keepalive tick - and a backtrace; then the console paths' `crash_restart` via `crashlog::restart_on_panic`, the rest end), and an async-signal-safe `sigaction` handler for SIGSEGV/SIGBUS/SIGILL/SIGFPE/SIGABRT (a `FATAL SIGNAL` line through `write(2)` on a debug.log fd opened at start, the terminal put back on the console paths with `tcsetattr`, then the previous handler - Rust's stack-overflow report - and the default action re-raised, so core dumps work again); Windows gets an unhandled-exception filter (`FATAL EXCEPTION 0x...`). The old handlers logged only in Debug mode (gated by 86f3b0a, 2026-03), allocated inside the handler and `exit()`ed; `-D`/`--multiuser`/`--local-server` had none. `crashlog::session(mode)` at each long-running mode's dispatch writes `session pid=N mode=...` (not on clay_web's stderr, where its start-up report marks the session - 2026-11-11; the exit and crash records still go there) and a marker `~/.clay/run/<pid>` that only an orderly exit removes: `crashlog::finish` (`exit (<reason>)`) runs from `atexit` on Unix and explicitly where Windows' `ExitProcess` skips it (`crashlog::exit_process(code, reason)`, the WebView's tao exit); attached clients record SIGTERM/SIGHUP themselves (`record_ending_signals`; the modes with an App have TF's handlers). At the next start each marker whose pid is gone becomes `previous session: ... crashed: <its CRASH/FATAL line>` (and a ✨ notice in the console, remote console, native GUI and web page - held until the world is off its splash) or `... ended without a record` (debug.log only: a logout looks the same). An exec (reload, crash restart) keeps the marker: the pid carries on. The native GUI calls `crashlog::reinstall_fatal_handlers` at its first frame (its graphics stack may install its own). A new exit path needs `crashlog::exit_reason` (or `exit_process`), never a bare `process::exit` on Windows. `CLAY_CRASHLOG_TEST=panic` panics a thread two seconds into a session. The crash counter (`platform::CRASH_COUNT`) is read once at start, resets after ten minutes, and is handed to a reload's successor (`sync_crash_count_env`); a crash restart passes its panic in `CLAY_CRASH_REASON` for `crashlog::restart_notice`.
- **`/update` is one command that updates what can be updated, one program at a time** (`src/selfupdate.rs`). The server's half runs through `App::start_server_update`/`finish_server_update` (console, GUI master, `-D` daemon; multiuser refuses) and answers a remote requester with `WsMessage::UpdateOutcome` before the `ServerReloading`; the client's own half (native core `start_update` → `Effect::SelfUpdate`, app.js `updateFlow` → `proceedOwnUpdate`, the SSH console's `update_flow`/`pending_update`) starts only after that answer - and after the next `InitialState` when the server reloaded - because the two can be the **same file** on the same machine, and two concurrent installs would write the same staging file; `selfupdate::exe_replaced()` then skips the download and just restarts. Every line names its program (`Server:` / `This GUI:` / `This console:`), since both sets land in the same output. Two traps: the server used to bounce a client's `/update` back as `ExecuteLocalCommand`, and the native GUI forwarded any bounced command it didn't know back to the server - a silent ping-pong that read as "`/update` does nothing" (its `local_command` now prints a line instead); and an *older* server still bounces, which every client treats as "the server has no remote update" and moves on, never re-sending. On Windows nothing can replace a running process, so a console restarts by starting the new `clay.exe` in the same window and waiting for it (`platform::exec_reload`; the remote console's `relaunch_and_wait`, after its loop ends and its `EventStream` is dropped - crossterm's wake thread reads console input itself, and the window's input is the successor's); the waiting copy still runs from `<exe>.old`, which Windows won't remove or replace, so the next install moves the exe aside to the first free `<exe>.old.<n>` (`free_old_exe_path`).
- **Stable and alpha versions** (user ruling 2026-11-23: "Version 1.<number>.0 will be best guess as a stable version. /update should only install the 1.<number>.0 version. /update --newest should download the most current "alpha" versions ... /update -f will still force the download of the stable version unless --newest is specified"; and the same day: "All update commands go to the newest stable release unless --newest is provided, then the newest stable or alpha version is provided (whichever is newest version wise)"). `platform::is_stable_version` is "three numbers, the last one 0, no suffix"; `platform::pick_release(list, newest)` takes the highest version in GitHub's release list (`/releases?per_page=100`, one request) by `is_newer_version`'s ordering - stable ones only unless `newest` - and decides by the version number alone, never by the list's order or GitHub's pre-release mark; drafts and tags that are not `vX.Y.Z[-suffix]` are never offered. `check_and_download_update(want, ..)` then compares with this build (skipped by `force`, so `/update -f` on an alpha goes back to the stable version) and says which kind it compared: `Already up to date (current: v1.8.3, latest stable: v1.8.0)` or `(..., newest: v1.8.3)`. **`selfupdate::UpdateWant { force, newest }` is the one carrier**: `parse` reads `-f`/`--force` and `--newest` in any order (the three parsers there were disagreed on that), `command()` builds what a client sends its server with `-f` first (a server before `--newest` reads only the first argument, and then installs its one kind), `from_ipc` reads the WebView page's four bodies (`update`, `update-force`, `update-newest`, `update-force-newest`); it replaced the bare `force: bool` in `Command::Update`, `ClientFlow`, `App::pending_update`, `Effect::SelfUpdate` and every caller. **Settings' "/update to newest"** (user request 2026-11-23, that label - `setup::UPDATE_NEWEST_LABEL`; `Settings::update_newest`, settings.dat and the reload state, default off) makes every update command a `--newest` one, `-f` and `clay --upgrade` included (the user's answer the same day; back to stable is "switch it off, then `/update -f`"): `App::start_server_update` adds it (`UpdateWant::with_setting`, the one place for the console and both handlers), an attached client adds the server's copy where its `/update` starts (native core `start_update`, the SSH console's `run_remote_command`, app.js `case '/update'`) so both programs take the same release, and `clay --upgrade [--newest]` reads it from that machine's settings.dat (`persistence::read_global_section`, no `App`). On the wire it follows Status Panel: `GlobalSettingsMsg.update_newest: Option<bool>` (`App::update_newest_shown`: `None` to a login that may not update the server - `policy.server_wide` - and from a server before it; a client then shows no switch), `UpdateGlobalSettings.update_newest` through `SettingsAdditions` (`None` = unchanged; ignored without `server_wide`); the SSH console keeps `App::update_newest_known`. Shown in every interface's General settings: console `/setup` (`add_update_newest_field`), native `windows/settings.rs`, app.js `#setup-update-newest-toggle`. **An alpha is published as a GitHub pre-release** (the release skill's Step 8, `release.sh`): every Clay up to 1.7.x asks `/releases/latest`, which is "the newest release not marked a pre-release", so that mark is what keeps them, and the README's `releases/latest/download/...` links, on the stable version. Not changed (found 2026-11-23, reported to the user): in app.js a typed `/update` goes to the server as plain text, so `updateFlow` and the page's own half run only on an older server's bounce - the intercept went in c62c567 and the 2026-10-13 rework did not bring it back; no shipped build is affected (no desktop asset has the WebView GUI, Termux can't install over itself).
- **`/version` in a client attached to another Clay names both builds** (user ruling 2026-10-19): `Clay: Local  <this program>` then `      Remote <the server>`, spaces kept (`crate::attached_version_lines`, app.js `attachedVersionLines`, pinned together by a test). The server's half is `InitialState.server_version_detail` (`version_detail()`; an older server's `server_version` stands in), so the client answers itself: the SSH/`--console=host` console, the native GUI unless `runs_clay()`, the WebView GUI unless `WEBVIEW_MASTER` (its own detail is injected as `CLIENT_VERSION_DETAIL`), the Android app in Run on Server (`ClayVersion.java` runs `libclay.so --version` from Java once per process - Java may spawn it; only the bundled *server* must never spawn). A browser page, a GUI running Clay itself and Run on This Phone still send `/version` to the server for its one line, as does a client whose connection is down for its own.
