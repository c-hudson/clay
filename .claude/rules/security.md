# Connection security

Design record for incoming-connection gating, the password on the wire, outbound TLS pinning and the always-TLS server. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08. Complements SECURITY-ROADMAP.md (design record, D1-D8) and SECURITY-NOTES.md (user-facing).

- `known_hosts.dat` - Trust-on-first-use TLS certificate pins (`host:port` -> hex SHA-256 of the end-entity cert DER), 0600 permissions. Written by `persistence::add_pin`/`replace_pin`, read by `persistence::get_pin`; enforced by `platform::danger_rustls::TofuVerifier` (every MUD, remote-console and WebView-proxy connection). Both halves of an entry are lower-cased (`persistence::normalize_pin_host`, applied in every accessor *and* in the loader so older mixed-case entries migrate rather than strand): hostnames are case-insensitive, so `MyHost:9000` and `myhost:9000` must be one pin — two pins means a rotated cert is only caught for whichever spelling was used first. Android's `CertPinning.java` — a genuinely separate implementation of this same TOFU model — has always lower-cased here; keep the two in agreement. SSH host keys share the file under `ssh:{host}:{port}` (`ssh.rs::host_key_pin_key`), which is also safe to fold.
Incoming connections are gated in `src/http.rs` before anything is served. Design record: `SECURITY-ROADMAP.md`; user-facing summary: `SECURITY-NOTES.md`.

- **Stealth path (`web_path` setting, default `"clay"`)**: web UI served only under `/clay/...`. Any other path from a non-localhost client is silently dropped (connection closed, zero response bytes) and records a ban strike — except `/favicon.ico` and `/apple-touch-icon*`, which drop without a strike. Empty `web_path` = legacy mode (UI at `/`, 404s as before). Localhost always works at both `/` and `/clay/` (the GUI WebView depends on this). Routing decisions live in the pure `decide_route()`; `SecurityGate` carries the shared allow-list/auth-key/ban-list state into all three server variants.
- **Accept-time IP gate** (`gate_connection()`): when `websocket_allow_list` is non-empty, non-listed non-localhost IPs are dropped *before* the TLS peek — no handshake, no certificate, no redirect (`GATE-DROP`, deliberately not a ban strike, or the knock below could never get through). Allow-list membership never skips authentication.
- **CLAY-KNOCK v1**: in-band auth-key preamble on the same TCP connection, before TLS/HTTP. Client sends `C7 4C 41 59 01 00`; server replies `C7 4B` + 32 random bytes; client sends raw `SHA256(auth_key || challenge)`; server acks `C7 06`. First byte `0xC7` disambiguates from TLS (`0x16`) and HTTP (ASCII) in the existing first-byte peek. A knocked connection may **WebSocket-upgrade at any path but never fetch a page** (`KNOCK-HTTP-DENIED`), and still performs normal WS auth. Android implements it in `NativeWebSocket.java` (`KnockSocketFactory`/`KnockSocket`, with fallback for old servers). `SecurityGate.auth_key` is a `KeySource`: the one Clay's key, or on `clay_multi` every user's (`instance::KeyIndex`, seeded from `~/.clay/users/*/settings.dat` at start and kept by `App::publish_auth_key`; each key compared in constant time, no early exit); `clay_web` has none, so a knock always fails there.
- **WS auth matrix**: no allow list → password or auth key from anywhere; allow list set → password only from listed/localhost/whitelisted addresses, everyone else must knock with the auth key. **The servers' logins** (`http::Backend::Multi`, `handle_ws_client`'s second phase): `MultiLogin::Users` takes a username + password.dat password (`instance::Credentials`, re-read per attempt; an unknown user and a wrong password are one answer) or a user's auth key (`KeyIndex` names the user, that user's Clay validates it as a single Clay does), `MultiLogin::Anonymous` takes anyone (`clay_web`); the connection is then `attach`ed to its instance's client table and event channel, and `release`d when it ends. A connection flood - more than `CONN_RATE_MAX` (30) new connections in `CONN_RATE_WINDOW` (10 s) from one address (`http::ConnRateLimiter` in every `start_https_server` accept loop; loopback never counted; a flooder's history is forgotten once struck) - is `CONN-FLOOD` and a `gate.strike`, so the D6 exemptions apply and the usual two strikes ban.
- **Ban exemption (D6)**: once an allow list is configured, the accept-time gate already drops every non-listed IP before it can reach any probe-strike site — so a probe strike can only ever ban a *legitimate, allow-listed* caller, never a scanner. `SecurityGate::strike()` is the one chokepoint every probe-strike site calls; it never bans an IP that's localhost, runtime-whitelisted, or matches a *specific* allow-list entry (exact IP, IP wildcard, or hostname pattern). A bare `*` allow-list entry does **not** confer this exemption — `*` means "let everyone reach the UI," not "nobody can ever be banned." `redirect_http_to_https()` (the plain-HTTP-on-the-HTTPS-port handler) reuses `decide_route()` directly instead of a separate reachability check, so it can never drift out of sync with it again — that drift was the root cause of a bug where an allow-listed user typing `http://` instead of `https://` got banned after two tries. Failed WebSocket password auth is the one exception: it still bans, and still applies to allow-listed IPs, via `BanList::record_auth_failure()` (threshold 5, not 2 — see `SECURITY-ROADMAP.md` D6). A connection that already knocked skips the "not in allow list" WS strike too (it proved a valid key; banning it would lock it out of its own recovery path).
- **Debugging**: `~/.clay/remote.log` records `HTTP-DROP`, `GATE-DROP`, `GATE-TIMEOUT`, `CONN-FLOOD`, the servers' `INSTANCE-START`/`INSTANCE-ATTACH`/`INSTANCE-ENDED` and `WS-INSTANCE-GONE` (a client whose Clay ended), `TLS-ON-PLAIN` (ClientHello on a plain-HTTP server — logged, never struck), `KNOCK-OK`/`KNOCK-FAIL`/`KNOCK-BAD-MAGIC`, `KNOCK-HTTP-DENIED`, `WS-PATH-DROP` alongside the existing `BANNED`/`CONN-LIMIT`/`TLS-*` events. A silent drop is intentional — expect zero bytes, not an error page. `log_remote_event()` is a no-op under `#[cfg(test)]` — tests must never append to a real user's `~/.clay/remote.log`.
  Output-sync diagnostics land in the same file: `SEQ-LEDGER` (a stored line the server never broadcast — always a bug, always names the line), `SEQ-HOLE` (a client gave up on a seq range it was never sent), `SEQ-AUDIT` (a client's ack vs. what it is owed; transitions always, steady states only under debug), plus the client-reported `SEQ-MISMATCH`/`DUPLICATE`/`OUT-OF-ORDER`. On a healthy instance none of these appear; any of them is the "the TUI shows a line the phone doesn't" class, and `/dump`'s per-world `broadcast_ledger` line localizes it. `SCROLL-JUMP` (a `CLIENT-LIFECYCLE` event from Android: code moved a view that was following live output more than 3 screens away; details include the recent render/scroll causes) is the signature of the keyboard/resume jump class. `WS-BAD-MESSAGE` (`type=.. err=.. len=..`) fires at the three sites that deserialize a raw `WsMessage` off the wire — the server's main WebSocket receive loop and both of the SSH remote console's receive sites (the InitialState wait loop and the main loop) — whenever a message fails to deserialize; this is the amplifier for every wire-shape bug (e.g. a missing `#[serde(default)]` on an `Option` field), so a message that used to vanish silently now names its `type` (best-effort, via a raw JSON probe) and the serde error.

**The Clay password never crosses a network in the clear.** Invariants, all enforced in code: (1) `GlobalSettingsMsg.ws_password` is always sent empty — clients get only `ws_password_set` — and `UpdateGlobalSettings.ws_password` empty means *unchanged*, never "clear" (a client that was never sent the password echoes `""` on every unrelated save; clearing is console-only). (2) A bare password hash or raw auth key (`challenge_response: false`) is accepted only from loopback (`websocket::plain_credential_allowed`) — it replays; clients answer only a ServerHello challenge and send nothing if it is missing (app.js `authenticate`/`tryAuthWithKey`, the three editor pages' `doAuth`). The one bare-hash sender is `AUTO_PASSWORD`, which only ever targets 127.0.0.1. (3) Plaintext `ws://` is used only to a loopback host (`util::is_loopback_host`; app.js `isLoopbackHost` in `buildCandidates`; the remote console/grep/import clients and `run_remote_webgui` refuse to fall back for a remote host). (4) A spawned GUI window inherits the parent's login in-process only (`InheritedAuth` → injected `INHERITED_AUTH`, or a same-origin `window.opener.__clayInheritAuth()`), never via a URL.

**Outbound TLS is pinned, not CA-verified (D7).** Every client-side TLS connection (MUD worlds, remote-console, WebView proxy, hot-reload proxy, `/connect`) uses `platform::danger_rustls::TofuVerifier`, not CA verification — Clay's own server and most MUDs are self-signed. Trust-on-first-use: pin `sha256(end_entity_DER)` in `~/.clay/known_hosts.dat` (`persistence::add_pin`/`get_pin`/`replace_pin`) silently on first sight; on a mismatch, **block** and surface old-vs-new fingerprint + a "trust new cert" action in all three UIs (`WsMessage::CertMismatch`/`TrustCertificate`, web `showCertMismatchDialog`, TUI `create_cert_mismatch_dialog`). **The signature-verification methods MUST do real verification** (delegate to `rustls::crypto`) — pinning the fingerprint alone is defeatable by replaying the public cert without its key. See `SECURITY-ROADMAP.md` D7.

**Other D7 invariants**: secret files go through `util::write_secret_file`/`secure_create_file`/`secure_append_file` (0600; `~/.clay` is 0700) — never plain `File::create` for anything holding a password/key/token. Static-secret comparisons use `util::constant_time_eq`. A `clay_multi` user's client reaches only that user's own `App` (the instance's client table), so no per-world owner check exists or is needed; a `clay_web` visitor's template is scrubbed of every secret (`Settings::visitor_template`, `WorldSettings::visitor_copy`), because `InitialState`/`GlobalSettingsMsg` hand an authenticated client the world passwords and the auth key. MUD text reaching the web client must be escaped — `app.js` `escapeHtml` (incl. quotes) + `sanitizeHtml` on output sinks, and any HTML-building helper (e.g. `convertDiscordEmojis`) must escape what it interpolates. GMCP media URLs are http/https-only with internal targets refused.

**The web server is always TLS-capable for remote clients; localhost is always plain (D8).** The single-user `/web` popup no longer has a Protocol setting — `web_secure` is kept in `Settings`/`GlobalSettingsMsg`/settings.dat only for wire/import compat, never read to choose HTTP vs HTTPS. `resolve_web_cert_files()` (main.rs) picks a user-provided cert (`websocket_cert_file`/`websocket_key_file` — "Custom Cert File: Yes" in the popup) if set, else an auto-generated self-signed cert whose PEM now lives in `Settings.web_cert_pem`/`web_key_pem` (public cert base64'd cleartext, private key base64'd-then-`secret()`-encrypted — same at-rest mechanism as `websocket_auth_key`), materialized to `~/.clay/cert.pem`/`key.pem` as a derived on-disk cache. In the TLS accept loop (`http.rs`), the existing first-byte-peek branch that used to redirect any non-TLS request to HTTPS now instead serves a **loopback** connection plain via `route_connection` (no handshake) — remote non-TLS requests still redirect. This is why the GUI WebView (`ws://127.0.0.1`) never sees a cert prompt while remote clients always get TLS. Auto-approval on the Clay↔Clay path needs no new work — the existing D7 `TofuVerifier` pinning already silently trusts on first connect and only blocks+prompts on a later mismatch, for every outbound Clay client (remote console, WebView proxy, Android). `-D` and `--multiuser` (`daemon.rs`) use the same always-TLS server now (their old plain-HTTP mode sent every login and settings message across the network in cleartext); `clay_multi` resolves its cert with `resolve_web_cert_files` on the operator's own App (the operator's settings.dat, so saving the generated PEM there is right). **`clay_web` never makes a self-signed certificate** (user request 2026-11-11: browsers warn about one and in-app browsers refuse it): web.dat's `cert_file`/`key_file` (checked by `custom_cert_problem`, an error at start, never a fallback) or, by user ruling the same day, **plain HTTP to everyone** - `start_https_server(server, tls: None, ..)` builds no acceptor, serves a remote plain request instead of redirecting it, and hands a ClientHello to `route_connection`, which logs `TLS-ON-PLAIN`. The one exception to D8: a visitor has no password to protect and the page itself arrived in the clear. app.js `buildCandidates` therefore allows `ws://` to a remote host only on a `WEB_FRONT` page whose `location.protocol` is `http:`; every other page keeps "plain ws only to loopback". No HSTS goes out plain (`is_https` gates all three header sites). `--local-server` binds `start_https_server` to 127.0.0.1 via `http_bind_host()`. Auth Key is read-only in `/web`/web-settings now; Copy/Regen/Delete live in a "Modify Key" sub-popup (TUI: `popup/definitions/modify_key.rs`; web/GUI: `showModifyKeyDialog` in `app.js`), with Regen/Delete reusing `App::handle_ws_key_request`/`handle_ws_key_revoke` (immediate effect, broadcast to all clients) rather than waiting on the popup's own Save. See `SECURITY-ROADMAP.md` D8.
