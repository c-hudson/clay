# Worlds, views and connections

Design record for world removal, the Activity world, Esc-w, Login Command, First Command, keepalive gag, timed prompts, hidden typed input, split output, chat worlds, `/dc`, the status display. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08.

- **A world leaves `App::worlds` only with `fixup_indices_after_remove` and a `WorldRemoved` broadcast** (`delete_world`, and `discard_initial_world` - the fresh start's placeholder, dropped when another world connects). The fix-up moves everything the server keeps by world index - the console's world and split, the editors, each client's world (`ws_client_worlds`, `WsClientInfo::current_world`), other views and map panes - the way every client moves its own list on `WorldRemoved`. `discard_initial_world` used to adjust only the console's index and tell no one: an attached GUI kept the placeholder, sat past the end of the list, and the world just connected showed none of its text (2026-11-04).
- **The Activity world is a real `World` with `is_activity` set** (user request 2026-11-05; user docs 10-multi-world.md). `App::ensure_activity_world` appends it after every other world at each start (none for a `clay_web` visitor, none while a world of the user's own is named Activity, whose name `reserved_world_name` then keeps for it); settings.dat skips it, the reload state keeps it by index (`is_activity=true`), and `WorldStateMsg.is_activity` tells every client. It is reached only by name: `App::find_world_typed` (`util::find_world_typed` in the native GUI, app.js `findWorldTyped`) adds `act` for `/world` and `/split`, and `switch_exclude` keeps it out of next/prev/Esc-w; `split_next_world` and every world list (selectors, Recent Worlds, TF `/listworlds`) skip it. `process_server_data` hands each packet's visible lines to `copy_to_activity` (after TTS), which gives **each interface its own copy** (user request 2026-11-05): only while that interface shows the Activity world, and never a line from a world that interface shows itself (its view, its split pane, its `/window`s - `client_shows`; the console's two panes - `console_shows`), so other interfaces never change what one sees; and when a world comes on screen in an interface, its lines already in that interface's copy go too (each line's first word is its world, `util::activity_line_world`: the console's and SSH console's `track_console_world` → `World::drop_activity_from`, the native GUI's `drop_shown_from_activity` from `report_other_views` over every window, app.js `dropShownFromActivity` from `updateStatusBar`). The console's copy is the Activity world's own `output_lines` (`console_showed_activity`), pushed with more-mode off and born viewed but **never broadcast** - the one exception to "every line in `output_lines` is broadcast", so the ledger and ack audits skip the world, `InitialState` sends none of it (no lines, `next_seq` 0), and `RequestScrollback`/`RequestHistory` for it get nothing. Each client (`activity_viewers`) is sent its own lines by `ws_send_to_client` as unnumbered `ServerData` (seq 0, no `end_seq`), so no seq rule, gap fill, more-mode or ▶ touches them; the clients also skip it in their own more-mode and Taskbar Alert. The label is `newbg::activity_label` before the MUD-tag-stripped text; blank and colour-only lines aren't copied (each would be the world's name alone). Each interface's copy starts empty: `note_activity_viewers` sends a client a `ServerData { flush, data: "" }` whenever it comes to or leaves the Activity world, and empties the console's buffer the same way; it runs at the start of every client message (both handlers), at every console draw (`track_console_world`) and before each copy - a new place that moves a view without one of those can leave stale lines. Only on the master (`is_master`): the SSH console draws through the same `track_console_world` and must leave its mirror to the server's flushes. Both the native core and the SSH console return after an empty flush; without that `split_lines("")` added a blank line.
- **Esc-w's fallback world is per viewer, and kept by name.** `App::calculate_oldest_pending_world_from(current, history)` is the one rule for the console and every client (TinyFugue's `world-q.tf`: active worlds oldest first, then "the last world you visited that is still connected", walking the history past any that disconnected). The console's history is `App::world_history`; a client's is `ClientViewState::history`, computed by `App::client_history_after` at every site that moves a client's view state - miss one and that client's Esc-w stops at "no activity", which is what happened to `--gui=host` when the fallback read the console's own `previous_world_index`. Names, not indices: adding or removing a world needs no fix-up (the index version needed five).
- **A world's Login Command runs where a login finishes, and only there** (user request 2026-11-04; `WorldSettings::login_command`, Edit World's Options card, the console's Login Cmd): `App::run_login_commands` splits it by line and then by `;` (`WorldSettings::login_commands`, the action splitter, `\;` literal) and runs each as an action's command (a `/` line through TF + `apply_tf_effects_now`, anything else `send_to_world`). It is called at the three places Clay's auto-login completes: `handle_connection_success` after the Connect/Lines lines (after TF's LOGIN hook), `advance_auto_login` after a Prompt/MooPrompt login's last answer, and `finish_fansi_login` (FANSI's held-back login; the two event-loop timers call `finish_due_fansi_logins`, they used to carry their own copies of the send). A new login path must call it too. Never run without Clay's login (no credentials, Auto Login None, `/worlds -l`, `%login` off): commands typed into a login screen become a character name. `UpdateWorldSettings.login_command` is an `Option` (`None` = an older client, unchanged). A `clay_multi` user's worlds are their own and run it as any Clay's do.
- **A keepalive's reply is gagged by one check, `World::is_keepalive_reply`** (`process_server_data`, `World::add_output` and its partial-line completion; user request 2026-10-31): the marker `##rand##` becomes (`telnet::keep_alive_marker`; Custom and Generic, at any time), or a Custom keepalive's Gag Text (`WorldSettings::keep_alive_gag_enabled`/`keep_alive_gag`: the console's `[✓] KA Gag` row, Space ticks it, the GUIs' "Gag Text" with its checkbox before the name), case and escape codes ignored, only within `telnet::KEEP_ALIVE_GAG_WINDOW` (30 s) of the keepalive (`last_nop_time`). Every world editor shows `telnet::KEEP_ALIVE_RAND_WARNING` (app.js's copy pinned by a test) while a Custom command lacks `##rand##`. `UpdateWorldSettings.keep_alive_gag_enabled`/`keep_alive_gag` are `Option`s: `None`, from an older client, leaves them. **A client never drops the reply**: it is a gagged line, kept and shown under F2 as the console shows it (app.js `isKeepAliveMarker` → `lineGagged`, the native `on_server_data`/`line_from_ts` set `gagged` on the marker; `hidden_line`/`isFillerLine` hide only escape-only lines) - both GUIs used to hide it for good, app.js dropping it before storing (user report 2026-11-01: "gagged messages don't seem to be sent to the GUI"). Nothing in the connect process leaves gagged lines out: `take_visible_range` lets them ride along without counting against the Remote Lines budget, in `InitialState`, the backfill, the gap fill and the archive page alike.
- **Only a guess comes from timing, and a guess never takes text out of the output** (user report and rulings 2026-11-03). Prompts come from GA/EOR (`PromptSource::Marker`, the only kind that sets `seen_prompt_marker` and so stops a Timed world guessing) or `promote_due_timed_prompts` (`Timed`: the MUD - Timed Prompt type, or any MUD world while TF's `%lp` is on, `timed_prompt_wait_for`). `WONT ECHO` marks nothing: thechattingzone.uk sends it at the top of its banner, and both the old 150 ms "WONT ECHO seen" timer (any paused line, every world type) and the old "text before a WONT ECHO" rule (the tail of whatever line a read ended in) took banner text for the prompt. A GA/EOR whose line went out in an earlier read (over `MAX_TEXT_HOLDBACK`, idle-flushed, or the marker in a packet of its own, as that server's EOR is) is an empty `TelnetEvent::Prompt` (`TelnetSession::released_mid_line`), and `App::handle_prompt` then takes the parked `trigger_partial_line` as the prompt. A guess clones the parked `trigger_partial_line` and sets `World::prompt_timed`. The server's next visible text or newline ends it in `process_server_data` (empty `PromptUpdate`), and the text joins its line. A line sent while it shows answers it: `World::answer_timed_prompt`, from `clear_prompt_after_send`, `send_to_world` and auto-login. The answer moves it to `World::answered_prompt`, which `process_server_data` emits ahead of the reply as its own line, skipping triggers, TTS and BGTEXT (and `close_notice` flushes it). Two traps: an invisible fragment after a guess must not re-arm the timer (it would take the same prompt twice for auto-login); and every reload re-arm checks `!prompt_timed`.
- **What the user typed is never shown, F2 included** (user ruling 2026-11-06). A sent line is kept in the world's buffer as a gagged `is_input` line (`App::capture_sent_line`) for `/recall -i`, `/quote #` and the log (`log_input_enabled`), and kept across `/reload` (flag `i`); `OutputLine::is_hidden` is the one rule the console and the SSH console draw, page and search by. Clients get it with no text (`OutputLine::wire_text`, in `TimestampedLine::from_output_line` and the three `ServerData` builders): an empty gagged line keeps the seq accounted for, and every client hides a gagged line with no text, F2 or not (app.js `lineIsDrawn`, native `Line::is_hidden`). A new path sending stored lines to a client must use `wire_text`, never `line.text`.
- **Split output (`/split`, `/unsplit`, Shift+Tab = `split_focus`) is each interface's own, and the focused pane's world *is* that interface's current world** (user request 2026-10-30; user docs 04-interface.md "Split Output"): the console's `current_world_index` (`App::split: Option<ConsoleSplit { other, focus_top }>`), the native core's `current` (`ui/split.rs` `OtherPane`), app.js `currentWorldIndex` (`splitPane`) - so the typed line, keys, `/world`, paging and TF's foreground world follow the focus with no rerouting, and only drawing, the bars, more-mode's per-pane height and "who watches what" know there are two. A focus change is no world switch (no ▶ release, no history entry). Rules that bite: **(1)** every "is the console watching this world" goes through `console_shows`/`console_watching` (both panes), the switch keys pass `split_exclude()` (console) or `exclude` on `CalculateNextWorld`/`Prev`/`OldestPending` (clients; ignored by an older server), and `activity_count` leaves out both worlds; **(2)** a client's other pane is an `OtherViews` world with its size (`dims` → `min_viewer_lines`/`min_viewer_width`/`shell_dimensions`), and `set_client_other_views` claims ▶ for a world that comes on screen and releases one that leaves - never the client's main world; **(3)** a focus swap must reach the server as ONE message, `MarkWorldSeen { other_views: Some(..) }`, applied before the world left is released: two separate messages release one pane's ▶ whichever order they go in; **(4)** the console keeps `output_height` = the focused pane's rows (paging, more-mode, TF `winlines` and NAWS stay right), with `pane_rows`/`output_area_rows` for the layout and `console_rows_for(world)` for the other pane's budget, and draws each `rendering::ConsolePane` with its rows offset by `y` (`compose_pane`); **(5)** in the native GUI and app.js the focused pane's view state is the window's own fields (`scroll`/`select`/`shown_world`; `#output-container`, `followBottom`) and the other pane's is swapped in to draw it or handle its mouse (`in_other_pane`, `withSplitPane`) - app.js's `#output-container` is always the focused pane, because its listeners are bound to that element, and a swap trades the two containers' worlds and DOM places instead. A server-run `/split` (an action, a macro, a TF binding) goes back to the client as `ExecuteLocalCommand` only if it said `UpdateViewState.splits`: an older client would bounce it back for ever. The split survives a reload (console reload state `split_other`/`split_focus_top`; native relaunch stash; app.js localStorage `clay_split_<server>`). **The panes' size is the top pane's lines** (user requests 2026-11-05): `/split -n <lines>` in every interface (one parser, `util::parse_split_args`, app.js `parseSplitArgs`; not split it splits, split with no world it only resizes; the console's `App::split_command` for both consoles), `/split +<lines>`/`-<lines>` (`SplitLines::By`: from the whole lines the top pane shows now - the console's `rendering::split_pane_rows`, native `split_lines_shown`, app.js `splitLinesShown` - clamped to what fits, and only while split, else `util::SPLIT_NOT_SPLIT`), and in the GUIs and web a drag of the bar between the panes, a line at a time. It is each program's own and kept for its next `/split`, split or not: the console's `App::split_top_rows` (reload state `split_top_rows`), the native `SplitSize::top_lines` (relaunch stash `SavedInput.split_top_lines`), app.js `splitTopLines` (in the `clay_split_<server>` record); unset is half each. Each pane keeps one line: the console clamps in `ui()`, the GUIs let flexbox do it (the top pane's basis is its lines and it may shrink, the bottom grows, each has a one-line min-height), so a short window never needs a measurement first. A press on the bar still moves the focus there first, at the press: the bar's More/History badge releases the focused pane's text on its click, so a swap at the release would release the wrong pane. A drag let go over the native other pane is not its "plain click" (`other_pane_mouse_up` checks the drag), and app.js's badge starts no drag (pointer capture would take its click).
- **Chat worlds are one session per world, ended only by dropping its `ChatHandle`** (`World::chat`). Every task of a session watches the handle's `watch` channel; `clear_connection_state` drops it and bumps `connection_id` so the session's in-flight `AppEvent::Chat` events go stale. All chat events go through `App::handle_chat_event`, called from `App::preprocess_event` before each event loop's `match` - it re-dispatches chat lines as `ServerData` (triggers, gags, archive, broadcast) and a lost session as `Disconnected`, so no loop carries chat logic of its own (the old per-loop Slack/Discord arms were missing from the GUI/headless and `-D` loops entirely). Rules: `process_server_data` must keep its MUD-only steps (MCP, BAMF, idler gag, FANSI, non-UTF-8 decode) behind `is_mud`; the keepalive must never reach a chat world (`World::wants_keepalive`) - an `IAC NOP` used to be POSTed into the channel; a chat line must never start with `[` (`strip_mud_tag` would hide the channel tag); a chat world's prompt is its send-target indicator (`App::refresh_chat_prompt`) and is not cleared on send (`World::clear_prompt_after_send`); own messages arrive as `SelfLines` and never fire triggers. Settings changes to chat fields go through `UpdateWorldSettings.chat` (authoritative, empty clears); the legacy fields keep "empty = unchanged" for older clients. `chat_settings_version` gates a one-time migration (`persistence::migrate_chat_settings`) and is written for every Slack/Discord world - never drop it from a chat world's save, or old worlds are re-migrated on every load. Any other world type carries no key: the loader stamps it current in memory (so a MUD switched to Discord later saves the version and is never taken for a legacy one) and the writer leaves it out.
- **A world's First Command goes out first, raw, with `%host%` the connecting client's address** (user request 2026-11-09, for the `clay_web` gateway: `REMOTE_HOST %host%` tells a MUD who is behind a shared Clay; user docs 08-settings.md). `WorldSettings::first_command` (settings.dat `first_command=`, escaped like `login_command`; `UpdateWorldSettings.first_command: Option` = `None` from an older client; `WorldSettingsMsg.first_command`), shown in all four world editors beside Login Command (console `WORLD_FIELD_FIRST_COMMAND`, app.js `#world-edit-first-command`, native `fields["first_command"]`). `App::send_first_command` runs at the top of `handle_connection_success`, right after the `is_mud` check and before the login branch, so it precedes Connect/Lines lines, a FANSI login held back and a prompt login alike; each line as typed (`first_command_lines`), blank lines dropped, `WriteCommand::Text` (the writer adds CRLF) - never through TF, so `%{x}` and the like are sent as they are. `%host%` is `World::connect_ip`, set by `spawn_world_connect` from `App::connect_origin_ip`: `ConnectOrigin::Client { client_id }`'s address through `util::normalize_client_ip` (an IPv4 peer of a dual-stack listener reads `1.2.3.4`, not `::ffff:1.2.3.4`), `127.0.0.1` for the console (commands.rs's own connect task sets it), the embedded GUI (client 0), an unknown client and TF's or a trigger's connects; an auto-reconnect keeps the last one; the reload state carries it (`connect_ip=`). An SSH-tunnelled client reads as `127.0.0.1`. `connect_daemon_world`'s own `skip_auto_login=false` sender is dead in production (every caller passes `true`); a caller passing `false` would log in before the First Command.
- **A connection ends through one path, and `/dc` really closes it.** `/dc`, a client's Disconnect and `-D`'s `DisconnectWorld` all go through `commands::disconnect_world`: `WriteCommand::Shutdown`, then a `connection_id` bump, then `clear_connection_state`. Dropping only the App's sender is not enough - the reader keeps its own clone of the writer channel, which is how `/dc` used to leave the socket open with the server's text still arriving in a "disconnected" world. A reader stops as soon as its writer does (`cmd_tx.closed()` in `spawn_telnet_reader`), and every close is reported as `AppEvent::CloseNotice` then `Disconnected`, both carrying a `telnet_reader::CloseReason` and the connection id. The telnet echo mask dies with the connection on **both** sides: `handle_disconnected` broadcasts `EchoMaskChanged{masked:false}` after `WorldDisconnected` when it was masked, and every client (native core, app.js, the SSH mirror) also clears `echo_masked` on `WorldDisconnected` - a MUD that negotiates ECHO off at its password prompt and then drops left attached GUIs showing `*` for every key typed into the next connection. `App::preprocess_event` (the one prelude before every loop's `match`, Slack/Discord included) turns the notice into Clay's message as `ServerData` - so triggers, Actions, the archive and the log see it as before - unless the connection is stale or TF's DISCONNECT hook is gagged (`App::tf_hook_gagged_for`, which judges `-w`/`-T` against the event's world). Connect failures go through `daemon::connect_tcp` and one `App::report_connect_failure` (ICONFAIL per failed address, then CONFAIL, with tf's "<world> <address> <port>: <reason>"); a successful connect's earlier failures arrive as `AppEvent::ConnectAttemptsFailed`. rustls reports a close without close_notify as `UnexpectedEof` - a server close, not a read error.
- **The MUD's status display (GMCP `Char.*`/MSDP: console status line, GUI/web status panel) has two switches** (user ruling 2026-11-02): Settings' Status Panel (`Settings::status_panel`, one for the instance, console `/setup` "Status Line") and each world's (`WorldSettings::status_panel`, Edit World; `/stats hide|show` and the GUIs' × on the panel set it). It shows only while both are on (`App::status_display_wanted`); the console's layout asks `App::status_line_rows`, never `World::stats_line_shown` alone. On the wire both are `Option<bool>` (`None` = a server before them: shown, no switch, no ×).

- **A disconnect's "Disconnected." is unseen only when nobody watches the world** (`handle_disconnected`, user report 2026-11-08): it compared against the console's `current_world_index` alone, so a remote GUI that disconnected the world it was viewing - the console elsewhere, or the server headless - had the world counted as activity the moment it switched away (the switch's `broadcast_activity` carried the stale count), cleared only by a visit, and never flagged again. Now `World::world_watched` decides, the line is born `viewed` while watched (as the final prompt line already was), and an unwatched disconnect broadcasts `UnseenUpdate` + the activity count at once, since nothing more arrives from that world to carry it. The three reload-time notices (MCCP2, TLS in two loops) use the same check.
