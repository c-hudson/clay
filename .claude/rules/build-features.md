# Build features

Design record for the compile-time features (`ssh-transport`, `shell-worlds`, `multiuser`, `web-front`) and every build line that must name them. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08.

**`ssh-transport`** (SSH-tunneled `--console`/`--gui`, see `src/ssh.rs`) is in `[features] default` in `Cargo.toml`, so any build WITHOUT `--no-default-features` gets it automatically. Any `--no-default-features` invocation must add it back explicitly or the binary silently loses `--ssh`/`--ssh-proxy` support (`--ssh` exits with "requires the 'ssh-transport' feature" instead of erroring on something more obviously wrong) - this bit us once already; if you add a new `--no-default-features` build command anywhere (a script, this doc, CI), include `,ssh-transport`.
**`shell-worlds`, `multiuser` and `web-front` are compile-time choices** (user rulings 2026-11-07, 2026-11-09). `shell-worlds` (the PTY and `alacritty_terminal`, `log`, `polling` as optional deps) is in `default` too, so the same trap applies: every `--no-default-features` line names it (build.sh, the three Termux scripts, `build-drobo5n.sh`, release.sh, sync-clay-builds.sh, the release skill's musl line) except `build-android-aarch64.sh`, the Android app's on-device server, which must never start a subprocess. The two server features are described in the next paragraph; neither is ever built with shell worlds (`compile_error!`). What `shell-worlds` gates and what stays in every build (a client must still work with someone else's server): the shell module stays declared and only the emulator is gated (`shell/session.rs`, `adopt.rs`, screen.rs's `render_rows`/`mode_msg` and the server-only `ShellScreen` methods, keys.rs's byte encoders); without it `ShellSession` is an uninhabited enum, so `World::shell` is always `None` and the call sites need no `#[cfg]`, the server-only `App` methods in `shell/app.rs` are no-ops, and connecting a shell world prints `shell::NOT_IN_THIS_BUILD` (the world still loads, shows and saves; a reload from a build that had shells closes the inherited PTY). `InitialState.shell_worlds` (`default_true`: an older server always could) tells clients, and every world editor offers Shell only when it is true or the world already is one (console `world_type_options(offer_shell)`, native `windows/worlds.rs` `world_types`, app.js `offerShellWorldType`). `clay --multiuser` without the feature prints `requires the 'multiuser' feature` and exits, as `--ssh` does. Unused `pub` items don't warn in this crate, so a gate missed shows up only by reading. Test all four sets: `cargo test` (shell worlds), `cargo test --no-default-features --features ssh-transport,native-audio,multiuser`, `cargo test --no-default-features --features ssh-transport,web-front`, `cargo test --no-default-features --features ssh-transport`.

**`multiuser` and `web-front` are the two server builds** (user request 2026-11-09, replacing the per-connection `--multiuser` model of 2026-11-07 - `UserConnection`, `multiuser.dat`, `World::owner`, `Action::owner`, `TelnetTarget::Multiuser`, `ChatOwner::Multiuser`, `broadcast_to_owner`, `handle_multiuser_ws_message` and `multiuser_typed_line` are gone; no migration of multiuser.dat, it shipped in no release). `multiuser` is `clay_multi` (a full Clay per user, `src/server.rs` `run(ServerKind::Multi)`), `web-front` is `clay_web` (an anonymous page onto one world, `run(ServerKind::WebFront)`); both are `[]` features whose only gated code is `src/server.rs` and main.rs's dispatch - everything else (`instance.rs`, `apploop.rs`, `http::Backend`, the policy checks) is in every build and tested by the default suite. main.rs refuses `multiuser`+`shell-worlds`, `web-front`+`shell-worlds` and `web-front`+`multiuser` with `compile_error!`. `build.sh` builds `./clay` (as before, feature-probed), then `./clay_multi` and `./clay_web` with `--no-default-features --features ssh-transport,<feature>` through `build_server`, **in their own target directory `target/servers`** (`--target-dir`; user report 2026-11-10: cargo names every binary `clay`, so the servers built last had left `target/release/clay` as `clay_web` - release.sh's Linux GUI asset and the user's own `target/release/clay --gui` got "this build is a server"), copying each to the repo root (`.gitignore`: `/clay`, `/clay_multi`, `/clay_web`); cargo's `target/release/clay` and the musl path stay the client. `--only clay|multi|web` builds one, `--multiuser` is `--only multi`. In a server build a start naming no interface or one-shot tool runs the server, `--console=host`/`--gui=host` still attach, and `--gui`/`--web-gui`/`-D`/`--console` without a host are refused ("this build is a server"). `--version`'s Features line names the feature; the release skill's check that no asset has `multiuser` applies to `web-front` too. Test all four sets (CLAUDE.md Build Commands).
