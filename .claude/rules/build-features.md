# Build features

Design record for the compile-time features (`ssh-transport`, `shell-worlds`, `multiuser`, `web-front`, `webview-gui`) and every build line that must name them. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08.

**`ssh-transport`** (SSH-tunneled `--console`/`--gui`, see `src/ssh.rs`) is in `[features] default` in `Cargo.toml`, so any build WITHOUT `--no-default-features` gets it automatically. Any `--no-default-features` invocation must add it back explicitly or the binary silently loses `--ssh`/`--ssh-proxy` support (`--ssh` exits with "requires the 'ssh-transport' feature" instead of erroring on something more obviously wrong) - this bit us once already; if you add a new `--no-default-features` build command anywhere (a script, this doc, CI), include `,ssh-transport`.
**`shell-worlds`, `multiuser` and `web-front` are compile-time choices** (user rulings 2026-11-07, 2026-11-09). `shell-worlds` (the PTY and `alacritty_terminal`, `log`, `polling` as optional deps) is in `default` too, so the same trap applies: every `--no-default-features` line names it (build.sh, the three Termux scripts, `build-drobo5n.sh`, `build-linux-aarch64.sh`, release.sh, sync-clay-builds.sh, the release skill's musl line) except `build-android-aarch64.sh`, the Android app's on-device server, which must never start a subprocess. The two server features are described in the next paragraph; neither is ever built with shell worlds (`compile_error!`). What `shell-worlds` gates and what stays in every build (a client must still work with someone else's server): the shell module stays declared and only the emulator is gated (`shell/session.rs`, `adopt.rs`, screen.rs's `render_rows`/`mode_msg` and the server-only `ShellScreen` methods, keys.rs's byte encoders); without it `ShellSession` is an uninhabited enum, so `World::shell` is always `None` and the call sites need no `#[cfg]`, the server-only `App` methods in `shell/app.rs` are no-ops, and connecting a shell world prints `shell::NOT_IN_THIS_BUILD` (the world still loads, shows and saves; a reload from a build that had shells closes the inherited PTY). `InitialState.shell_worlds` (`default_true`: an older server always could) tells clients, and every world editor offers Shell only when it is true or the world already is one (console `world_type_options(offer_shell)`, native `windows/worlds.rs` `world_types`, app.js `offerShellWorldType`). `clay --multiuser` without the feature prints `requires the 'multiuser' feature` and exits, as `--ssh` does. Unused `pub` items don't warn in this crate, so a gate missed shows up only by reading. Test all four sets: `cargo test` (shell worlds), `cargo test --no-default-features --features ssh-transport,native-audio,multiuser`, `cargo test --no-default-features --features ssh-transport,web-front`, `cargo test --no-default-features --features ssh-transport`.

**`multiuser` and `web-front` are the two server builds** (user request 2026-11-09, replacing the per-connection `--multiuser` model of 2026-11-07 - `UserConnection`, `multiuser.dat`, `World::owner`, `Action::owner`, `TelnetTarget::Multiuser`, `ChatOwner::Multiuser`, `broadcast_to_owner`, `handle_multiuser_ws_message` and `multiuser_typed_line` are gone; no migration of multiuser.dat, it shipped in no release). `multiuser` is `clay_multi` (a full Clay per user, `src/server.rs` `run(ServerKind::Multi)`), `web-front` is `clay_web` (an anonymous page onto one world, `run(ServerKind::WebFront)`); both are `[]` features whose only gated code is `src/server.rs` and main.rs's dispatch - everything else (`instance.rs`, `apploop.rs`, `http::Backend`, the policy checks) is in every build and tested by the default suite. main.rs refuses `multiuser`+`shell-worlds`, `web-front`+`shell-worlds` and `web-front`+`multiuser` with `compile_error!`. `build.sh` builds `./clay` (as before, feature-probed), then `./clay_multi` and `./clay_web` with `--no-default-features --features ssh-transport,<feature>` through `build_server`, **in their own target directory `target/servers`** (`--target-dir`; user report 2026-11-10: cargo names every binary `clay`, so the servers built last had left `target/release/clay` as `clay_web` - release.sh's Linux GUI asset and the user's own `target/release/clay --gui` got "this build is a server"), copying each to the repo root (`.gitignore`: `/clay`, `/clay_multi`, `/clay_web`); cargo's `target/release/clay` and the musl path stay the client. `--only clay|multi|web` builds one, `--multiuser` is `--only multi`. In a server build a start naming no interface or one-shot tool runs the server, `--console=host`/`--gui=host` still attach, and `--gui`/`--web-gui`/`-D`/`--console` without a host are refused ("this build is a server"). `--version`'s Features line names the feature; the release skill's check that no asset has `multiuser` applies to `web-front` too. Test all four sets (CLAUDE.md Build Commands).

**`webview-gui` is built for Termux and nothing else** (user ruling 2026-11-16, ending the 2026-10-09 "kept as a backup" on desktops: the Linux `-gui` asset held both GUIs, so it was linked against WebKitGTK and could not start at all - not even `--console` - on a desktop without it, a stock Kubuntu among them; the native-only build needs 12 system libraries where the two-GUI one pulled in 127, and the WebView code was 3.6 MB of 111). None of its code went: it is a compile-time option (`cargo build --features webview-gui`), and the only fallback there is - no script and no running Clay turns to it by itself. What builds it: `build-termux-aarch64-gui.sh` and `build.sh` on Termux (`if $IS_TERMUX; then add_webview_if_available`; `check_webview`'s desktop arms are kept as the record of what a build that asks for it needs). What no longer does: `build.sh` anywhere else (a desktop that can't build the native GUI gets a build without a GUI and is told what is missing; the retry after a failed native build no longer adds it), the release skill's Linux GUI, Windows and macOS lines (`native-audio,native-gui`), and the two local scripts `release.sh` and `sync-clay-builds.sh`. The skill checks it: the Linux GUI asset's `--version` and `ldd`, and the text `web-gui attached to` (compiled only under the feature) absent from the three desktop assets and present in `clay-termux-aarch64`. A build with the native GUI and without the WebView one opens the native GUI for `--web-gui[=host]` (`platform::web_gui_to_native`, main.rs before the `--gui` checks; one line on stderr and in debug.log, `WEB_GUI_NOT_BUILT`): installs up to v1.7.36 restart with the flag they were started with (`platform::restart_args`), so without it a Clay in the WebView GUI would have ended, connections and all, at the `/update` that brought the first native-only build. `/update`'s asset names are unchanged (`get_platform_asset_name`: every non-musl x86_64 Linux build takes `clay-linux-x86_64-gui`, which is why a native-only build updating into the two-GUI asset used to stop starting on such a desktop). Checked the day of the change: `cargo +1.98.1 check --features native-audio,native-gui` passes on the Windows VM and (`--target x86_64-apple-darwin`) on the Mac VM, from a scratch copy of the tree. v1.7.37 was the first release built this way on all three desktops (the skill's checks passed); its Windows and macOS builds were made in the VMs and not run there. And live on Xvfb: v1.7.36's two-GUI build in `--web-gui`, its file replaced by the native-only build, `/reload` - same pid, the native window, the MUD connection never closed, and the output says why (`platform::note_restart_without_web_gui`, after "Reload successful").

**The Linux release assets are built by two scripts, never a plain cargo line** (user request 2026-11-18). `build-linux-gui.sh` makes `clay-linux-x86_64-gui` against glibc 2.31: linked on this machine it needed 2.43 (`acosf`/`atan2f`/... took new symbol versions in 2.43), so Ubuntu 24.04, Mint 22, Debian 13, Fedora 43 and RHEL 9/10 couldn't start it; it links against `tools/glibc-sysroot.py`'s Ubuntu 20.04 sysroot (gpgv-checked) with this machine's gcc and Rust, and fails unless the binary needs nothing above 2.31 and starts under that sysroot's loader with `LD_BIND_NOW=1`. A new `-sys` crate that asks pkg-config for a library needs its focal `-dev` package in the tool's `ROOTS`. `build-linux-aarch64.sh` makes `clay-linux-aarch64-musl` (the x86_64 musl build's features) with Zig as the C compiler, fetched into `~/.cache/clay-zig` with a pinned SHA256. `/update` picks the asset by CPU as well as OS (`platform::release_asset_for`, pinned to the skill's upload list by `every_update_asset_is_released`): ARM64 Linux takes the ARM64 asset unless the build has a GUI, and no other CPU ever takes another CPU's binary. Details: the release skill's machines.md.
