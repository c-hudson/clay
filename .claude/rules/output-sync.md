# Output sync between the server and its clients

Design record for seq numbers, broadcast, the ledger, client dedup, gap fill, the per-line ▶ indicator and its styles, followBottom, RequestState. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08. Complements PROTOCOL-ROADMAP.md (Phases B-G), the design record.

- **WebSocket InitialState**: `build_initial_state()` sends only `output_lines` (NOT pending_lines) to avoid duplicates. Partial lines excluded from broadcasts. A client opens on the world it showed a moment ago or remembers (app.js localStorage `clay_last_world_`, native `prefer_world`) only if that world has connected since the server started (`was_connected`, kept by a hot reload, cleared by a cold start): else the server's current world, else the first that has (app.js `startWorldIndex`, client.rs `start_world`, one rule). A browser coming back to a world Clay had restarted without opened on it blank with no name on the bar (user report 2026-11-01); a resync stays on an unconnected world the window was already showing.
- **`World::output_lines` is always sorted by `seq`**: every release-path broadcast (`App::broadcast_released_lines`) and the seq-drift fix's `ServerData.end_seq` field depend on this. The invariant is maintained by routing a gagged line into `pending_lines` instead of `output_lines` (`process_server_data`'s `hold_gagged_in_pending`) whenever more-mode is on, the world is paused, and pending lines are already queued — otherwise a gagged line could get a newer seq and land in `output_lines` ahead of older, still-pending lines. See PROTOCOL-ROADMAP.md's seq-drift-fix Phase B, Step 4.
- **Remote clients dedup output by exact seq membership, not a high-water mark** (PROTOCOL-ROADMAP.md Phase C). `app.js` tracks `world._seenRanges` — coalesced inclusive ranges of every seq the server has delivered — and drops a line only when its exact seq is already present (`hasSeenSeq`/`hasSeenRange`). The old `_max_seq`/`_seqGaps` pair was a one-way ratchet: a mark pushed past the client's real buffer by any server-side ordering slip ate that world's output permanently *and* re-dropped its own repair. Record ranges for the whole delivered batch span, never per surviving line, or client-side display filtering punches phantom holes. The server independently audits each client's `PongCheck.acked` against `World::deliverable_high_seq()` (`App::audit_client_acks`) and pushes `ResyncRequired` at a world stalled across two keepalives — so a *new* poisoning path self-heals instead of needing a fifth round of one-path-at-a-time fixes. If you add a broadcast site, the thing that still matters is the sorted-by-seq invariant above; the client no longer depends on it for correctness.
- **The ▶ new-text indicator is owned per line, per viewer** (PROTOCOL-ROADMAP.md Phase D). `OutputLine`/`TimestampedLine` carry `viewed: bool` + `display_id: Option<u64>`; a client draws ▶ iff `display_id` is its own id (`InitialState.your_display_id`, derived from the stable `AuthRequest.client_uid` so it survives a reconnect). A line arriving while anyone is viewing is born `viewed` and can never be ▶ for anybody; the first client to *display* an unviewed line claims it, and the `!viewed` latch means a second client neither steals nor clears that marker. Claims/releases go to **one** client (`ClaimedNew`/`ReleasedNew`), never broadcast — that broadcast is exactly what made the old shared `new_from_seq`/`viewed_from_seq` watermark wipe other clients' markers on every world switch. Two traps: unviewed lines are **not** a contiguous tail (`viewed` flips with who's watching), so a claim must sweep the whole buffer and `ClaimedNew` must carry a seq list rather than a range; and backgrounding is **not** a disconnect (Android keeps the socket open), so it must be signalled via `ClientVisibility` — `WS_VIEWER_GRACE` is 10s and only covers transport blips. **`ClientViewState.visible` and `ClientViewState.paused` are not interchangeable**: both keep a client out of `ws_client_viewing`, but `paused` means only `/remote --pause` and is reported back to the client as its `PAUSED` badge by `handle_request_state`. Backgrounding writing into `paused` (as it briefly did) makes a resync landing in the background window light that badge with nothing to clear it on return. The console's own equivalent is `App::console_paused` (`/remote --pause console` from any interface, user request 2026-10-30; any key or paste at the console resumes it, `App::console_input`), and `/pause` (user request 2026-11-03, `App::pause_other_interfaces`) pauses every interface but the asker's - the console too when a client asks, and never a connection with the asker's owner id (its other tabs and windows). A paused client resumes on any use (user request 2026-11-04): a key, press, touch, wheel turn or menu choice sends `ResumeSession` once (native `ui/activity.rs` + core `user_active`, app.js `noteUserActive`; gated by `InitialState.resume_session`), and every resume (`App::resume_client_sessions`, also behind `auto_resume_if_user_action`) resumes all the interface's paused connections. "One interface" is `App::same_interface`: one owner id AND one `AuthRequest.instance_id` (`util::process_instance_id`, per process: the native core sends it, the WebView host injects it as `CLAY_INSTANCE_ID`; empty from a browser or the phone app) - two GUIs on one machine share a `client_uid` (one native-gui.dat, one WebView localStorage), so by owner id alone `/pause` in one skipped the other. A pause is a connection's, so both clients clear the PAUSED badge at every `InitialState`: kept, it outlived a reconnect (a server `/reload`) and nothing ever took it down, since the new connection isn't paused and is never told so. Every "is anybody watching this world" decision goes through `App::world_watched` (`console_watching` || `ws_client_viewing`), never `world_idx == current_world_index` alone, and `run_app`'s redraw doesn't mark the world seen while it is set. **A client must never hold a marker the server doesn't** (user report 2026-10-19: lines stayed ▶ however often the Android app switched away and back): leaving a world releases only what the server holds, so such a marker never clears. Three ways it happened: the reaper released an expired connection's markers though the same owner had reconnected - a reconnect is a new connection under the same owner id, so `reap_stale_ws_client_worlds` now skips an owner that is back; a release told only the connection that asked, though two can share an owner id (an Android `/window`, browser tabs: one localStorage `client_uid`), so `release_world_for` tells every live connection of the owner; and a client keeps its own lines across a reconnect and in its disk cache, old markers included, so `WorldStateMsg.own_new_seqs` lists every line the client owns, sent or not, and app.js `setOwnMarkers` / native `set_own_markers` apply it. **The marker has styles** (`Settings::new_indicator: NewIndicator`, Setup's New Indicator select: None | Character | Background | Custom, user requests 2026-10-28, one word each because the longer labels didn't fit a phone; the old bool is gone): the `▶ ` character, which is text and so takes `NLI_PREFIX_WIDTH` off the console's wrap width (`Settings::nli_prefix`), or a green glow behind the first 4 cells of every row of the line, fading to the theme's background (`Settings::nli_glow`; `src/newbg.rs` is the one source of the cells' colours - the console prints them with `newbg::glow_row`, fading to black or white by the console theme, the native GUI paints a quad per cell from `StyledLine::new_glow`, app.js builds the same stops into `--new-glow` for `.line.new-glow`), which is behind the text and reserves nothing. **Custom** (`NewIndicator::Custom(i)`, named `custom:<key>`) is the same glow starting at one of `newbg::SCHEMES` (ten, each about as dark as the green; app.js `NEW_GLOW_SCHEMES` is pinned to it): `NewIndicator::glow_start` / `Settings::nli_glow_start` give the first colour for both background styles. Its Setup entry carries the scheme (`setup::new_indicator_options`, "Custom (Teal)", the first scheme when none is set), and picking it - Enter on it in the console, a pick in the web page and the native GUI, never a key step - opens the picker, titled `NewIndicator::PICKER_TITLE` ("Custom Background"; console `glow_scheme` popup with `ListItemStyle::swatch` cells, app.js `showGlowSchemeDialog`, native `dialogs::small::GlowScheme`): each scheme drawn as `newbg::SAMPLE_WORD` ("Clay") over its four cells fading to the console's black or white or the GUI's own background. Everything about *which* lines and *when* is shared, and `nli_drawn()` still means "some style is on" (the old-context rows, `%textdiv`). A `/highlight` colour covers the glow. On the wire both go: `new_indicator` by name and `new_line_indicator` as the bool an older peer reads (`NewIndicator::from_wire`; a server keeps its style when an older client's save sends only `true`), and settings.dat writes the bool before the name so an older build still reads on/off while the name wins on load.
- **Every line added to `World::output_lines` must be broadcast** (PROTOCOL-ROADMAP.md Phase E). `App::add_output`/`add_output_to_world`/`emit_client_lines`/`process_server_data` all do; a raw `output_lines.push(...)` or a bare `push_line_respecting_pending(...)` does **not** — the TUI renders it and no client ever sees it, and the consumed `seq` leaves a permanent hole in every client's delivered-range tracking. Use `App::push_and_broadcast_line` (push + broadcast iff it landed in `output_lines`, `end_seq: Some(seq)` always). A site inside `for world in &mut app.worlds` can't broadcast from there — collect and emit after the borrow ends. Six such sites existed, each duplicated 2-3x across the console/headless/daemon loops, which is precisely why they drifted; prefer one shared helper over patching a copy. Related: a broadcast carrying `seq: 0` for a line that *was* stored with a real seq is the same class of bug — the line arrives but its seq is never recorded, so the ack audit sees a permanent gap.
- **The server audits itself against a broadcast ledger** (PROTOCOL-ROADMAP.md Phase F). `World::broadcast_ledger` records every seq actually put on the wire (same coalesced-range algorithm as `app.js`'s `_seenRanges`, fed from `App::note_broadcast` in the two fan-out helpers — `ws_broadcast`/`ws_broadcast_to_world`, deliberately NOT `ws_send_to_client`, since a single-recipient send is not delivery to everyone). `App::audit_broadcast_ledger` runs on every `PongCheck` and enforces the one invariant this whole bug class violates: **every line in `output_lines` below `pending_floor_seq()` must have been broadcast.** A violation is logged as `SEQ-LEDGER` (with the line's text) and re-broadcast, so a *new* leaking path self-heals and identifies itself instead of costing another user report — six paths have been fixed one at a time already. `/dump` prints the ledger per world; one range spanning `(0, next_seq-1)` is healthy, more than one is the signature. Not a violation: pending-held lines, the newest line (a broadcast may be in flight), an outstanding partial. When you add a `ServerData` site with a real seq, `end_seq` must be `Some(..)` — a bare `seq` reads as "not a real seq" on the client whenever it is 0.
- **A client that can't fill a gap must give up on it, not retry forever.** `requestGapFill()` anchors on `contiguousFrontier()`, so a seq the server can no longer produce (Ctrl+L's selective flush and a splash clear remove lines from `output_lines`; the archive prepend caps it at 10k) freezes that anchor: every reply re-delivers only what the client already has, `backfill_complete` stays false, and the `ScrollbackLines` handler re-requests the identical range without bound. `closeOldestSeqHole()` after 2 no-progress replies is the only terminating outcome; the loss is reported via `ReportGap` → `SEQ-HOLE` in `remote.log` rather than silently absorbed. Similarly, `evaluate_ack_audit`'s stall suppression is time-bounded (`AUDIT_REFIRE_INTERVAL`), never permanent — the likeliest cause of a stall is a full outbound channel, which is also what drops the `ResyncRequired` meant to fix it.
- **A headless server claims no ▶ for a console it doesn't have** (deferred bug G1, 2026-10-28). `App::switch_world` is the console's switch, and its `CONSOLE_DISPLAY_ID` release/claim run only under `console_tui` (so does the release-pending fallback that hands the current world's lines to the console); handler B's typed `/worlds` calls it for the server's foreground world (TF's WORLD hook, media) and used to take the lines from the GUI whose `/worlds` it was, whose own claim then got `ClaimedNew{[]}` and dropped its guess. A client's switch is recorded by one `App::ws_client_view_world` in both handlers, and `WorldSwitched` goes to the requester only (handler B broadcast it, and every attached SSH console followed). The SSH console answers a `WorldSwitched` that moves it with `MarkWorldSeen{new, previous}` (as it does `CalculatedWorld`) and sends none for the `ExecuteLocalCommand /world` that follows a typed `/worlds` onto a view already there - it used to move silently, so the server never released the world it left.
- **Only the user un-pins the output view** (`app.js` `followBottom`). Whether the view follows live output is one explicit flag: set by reaching the bottom (any means) and by `scrollToBottom()`, cleared ONLY by a scroll that moved the view **up** within `USER_SCROLL_WINDOW_MS` of user scroll input (touch/wheel/pointer on the output, or a scroll action/PgUp/PgDn - `noteUserScrollIntent()`). Every "was the user at the bottom?" decision (ScrollbackLines branches, resize handlers, `withOutputScrollGuard`, `setFontSize`, `appendNewLine`'s tail, more-mode's pause, the render-window grow branch) reads `followBottom`, never raw `isAtBottom()`: that geometry is wrong for a following user whenever the Android IME shrinks the view, lines land between frames, a setting reflows the buffer, or - after a resume - every event queued in the background fires at once. Deriving the user's state from scroll events is what let a code-caused scroll pause more-mode and let the grow branch add 500 lines above the view: the "keyboard opens after resume and it jumps up hundreds of lines and stays there" report, three rounds of it. A `ResizeObserver` on the container and `#output` re-pins a following view after any layout change; a code-caused drift of a following view re-pins in the scroll handler and, if over 3 screens, reports `SCROLL-JUMP` (`recordClientEvent` → `CLIENT-LIFECYCLE` in `remote.log`, with the recent render/scroll causes). If you add a new user-driven way to scroll the output, call `noteUserScrollIntent()` in it, or scrolling up that way will be undone.
- **`RequestState` is not a reconnect.** Its `InitialState` is byte-identical to the one answering an `AuthRequest`, but no resume list was sent and the server pushes no unprompted replay. Any client-side "worlds I asked to resume" record must be consumed by the single `InitialState` that follows the `AuthRequest`, never held until socket close — otherwise every resync looks like a reconnect and the client both skips its own catch-up and waits forever for a replay that never comes. This is the Android post-wake path, so it fails on every wake.
  Output-sync diagnostics land in the same file: `SEQ-LEDGER` (a stored line the server never broadcast — always a bug, always names the line), `SEQ-HOLE` (a client gave up on a seq range it was never sent), `SEQ-AUDIT` (a client's ack vs. what it is owed; transitions always, steady states only under debug), plus the client-reported `SEQ-MISMATCH`/`DUPLICATE`/`OUT-OF-ORDER`. On a healthy instance none of these appear; any of them is the "the TUI shows a line the phone doesn't" class, and `/dump`'s per-world `broadcast_ledger` line localizes it. `SCROLL-JUMP` (a `CLIENT-LIFECYCLE` event from Android: code moved a view that was following live output more than 3 screens away; details include the recent render/scroll causes) is the signature of the keyboard/resume jump class. `WS-BAD-MESSAGE` (`type=.. err=.. len=..`) fires at the three sites that deserialize a raw `WsMessage` off the wire — the server's main WebSocket receive loop and both of the SSH remote console's receive sites (the InitialState wait loop and the main loop) — whenever a message fails to deserialize; this is the amplifier for every wire-shape bug (e.g. a missing `#[serde(default)]` on an `Option` field), so a message that used to vanish silently now names its `type` (best-effort, via a raw JSON probe) and the serde error.
