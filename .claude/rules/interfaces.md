# Interface parity and per-interface settings

Design record for every-interface parity, the two server handlers, `/note`, `/help`, `/info`, Settings per interface, fonts and weights, input height, SettingsAdditions, Icon Bar/Tabs, Screen Reader, the Android server's rules. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08.

- **`/note` is one function for every console** (`App::run_note_command`: `/note`, `/note -l`, `/note <file>`), called by the local console's `handle_command` and by the SSH remote console's one dispatcher (`remote_client::run_remote_command`). A world's notes are the server's: a remote console asks (`RequestNoteEditorState`, `pending_note_open`/`pending_note_list`) and Ctrl+S sends `UpdateNote` (`save_editor_content`'s `!is_master` branch). **`/note <file>` is a file on the main instance's machine from every interface** (user ruling 2026-10-16): a client's `/note <file>` reaches `App::ws_open_file_for_client` (both handlers), which sends that client `FileEditorState`; its Save is `SaveFile`, answered by `FileSaved` (the editor closes on success); `/restrict file` refuses both. A client sends `SaveFile` only for a `FileEditorState` it got, so an older server never sees one. The web/Android/native Notes List (`/note -l`) fetches each `has_notes` world with `RequestNoteEditorState`. The editor's keys are `input_handler::handle_editor_key`, asked by both consoles before popups (so Ctrl+S saves rather than pausing output). `fixup_indices_after_remove` and the remote `WorldAdded` move the editor's world index (notes and MCP edit alike) with the worlds - `UpdateNote`/`McpEditSet` are by index.
- **`/help` has one first page and one text per topic.** The console's first page is `popup::definitions::help::HELP_LINES`, and TF's bare `cmd_help` returns it: that is what an SSH console's `/help` gets from the server, and a second copy there had drifted. The console looks a topic up in help.rs's `get_topic_help` first and every client in `cmd_help` first, so a topic both files defined showed different text by interface (a GUI's `/help version` said "Display Clay version information."); `every_clay_topic_is_answered_the_same_by_tf` fails when a `cmd_help` arm shadows a help.rs topic. The browser editors (theme/action/keybind) are `/help web`'s, never the first page's (user ruling 2026-11-04: they need `/web` set up first); the web/GUI Help page's cards (app.js `buildHelpQuickStartCards(touch)`) have a touch and a desktop wording, and the native `windows/help.rs` `CARDS` is the desktop one, pinned by `the_cards_are_app_js_desktop_wording`.
- **Each interface's Settings shows only what acts there** (user ruling 2026-10-26), and a hidden setting is only hidden: its value is still sent back by Save. Console and SSH console `/setup`: no GUI Theme, Keyboard Visible, Tabs or Icon Bar (`setup::CONSOLE_HIDDEN_FIELDS`, kept with `visible = false`). Web page (`showOnlyThisInterfacesSettings`, run at every opening): no ZWJ Sequence (console only); Keyboard Visible only on a phone/tablet layout (it also acts in a mobile browser, not just the app); no Clear Input on Send on a phone (phones always clear); no Phone/Tablet font size in the WebView GUI (`WEBVIEW_MODE`, a desktop). Native GUI: no ZWJ or Keyboard Visible, Font tab Desktop size only, and General's card puts the switches on the left, only as wide as they need, and every choice (Text Reveal included) on the right with the rest of the width - halves squeezed the choices' text (user report 2026-10-26); the web page's General card is the same (`.settings-two-column > .settings-column:first-child`, flex 0 0 auto), except on a phone, where the two columns are two full-width cards, one above the other (`body.device-phone .settings-two-column`, user request 2026-10-28: side by side, the choices were squeezed off the screen). Settings that act on the server stay everywhere. A new setting goes only where it has an effect. **One exception by user ruling (2026-10-27): Separator Style** (`Settings::separator_style`, the console's bar: Clay (value `web`, labelled "Web" until 2026-10-28) or TinyFugue, default Clay, `SeparatorStyle::OPTIONS` the one list) is one global setting shown in every Settings window - console `/setup` (`SETUP_FIELD_SEPARATOR_STYLE`), web (`setup-separator-style-select`), native (`SettingsView::separator`) - and travels as `UpdateGlobalSettings.separator_style` (`Option`, `None` = unchanged; the Theme Editor's own `UpdateSeparatorStyle` still works), every site through `App::set_separator_style` (see the TF status line bullet: it is TF's line's look too, and TinyFugue → Web resets TF's status line). The console's own Setup save broadcasts `GlobalSettingsUpdated` for the same reason a client's does: a GUI's Save sends back the copy it was last sent, so a console-side change it never heard of was put back.
- **Every interface does what the main instance does** unless the user ruled it interface-specific (see the memory note; ask before leaving one out). Two traps: **there are two server handlers** - only the console TUI master uses handler A (`App::handle_ws_client_msg` / `handle_ws_send_command_impl`); `--local-server` (the Android app's on-device server), the WebView GUI master, the native GUI's in-process Clay and `-D` all use handler B (`daemon::handle_daemon_ws_message`) - so a client-facing behaviour goes in one shared `App` method both call (`ws_tell`, `ws_say`, `ws_ban_list`, `ws_remote_attach`, `toggle_world_gmcp`, `handle_client_visibility`...), never into one handler's arm. And **a client's typed line is routed as the console's is**: `App::client_line_for_tf` (both handlers' outer entry, never the internal re-dispatch, which would loop) sends `/N pattern`, a user macro's name and, with `%sub` on, any `/` line to TF first. What a client's command leaves for an input line, a title or a filter (TF's `/input`, `/grab`, `/dokey`, kb*, `/xtitle`, `/limit`) goes back to that client (`App::client_keyboard` is its input line while it runs; `send_client_tf_ops` sends `InputOps`/`SetTitle`/`LimitOp`) - it used to be applied to the console's input on the console's next command. A server-only MCP editor: `handle_mcp_event` opens the console's editor only when `console_tui`. A client→server message added for this kind of work is gated like `OtherViews` (`InitialState.expand_line` for `ExpandLine`).
- **`/info [world]` is one server-built report** (`src/info.rs`, user request 2026-11-06; user docs 05-commands.md): `App::build_info_report` (multiuser: `build_multiuser_info_report`, only the user's own connection) makes an `InfoReport` (sections of key/value rows with a tone, plus free lines), `report_lines` turns it into text. The console prints it (`emit_client_lines`); a typed `/info` in app.js, the native GUI and the SSH console is caught by the client and asks with `RequestInfo` (gated by `InitialState.info_report`), and the `InfoReport` reply opens a window (app.js `renderInfoDialog`, the WebView GUI's POPUP_MODE `info` window, native `windows::Kind::Info`) or prints, with the client's own section after it (`own_process_section` when it is attached to another machine). An `/info` the server runs (an older client, an action, a macro) answers in text by `ws_tell` (`ws_info_text`). A static snapshot by user ruling: no refresh. What the report reads that nothing else kept: **`ConnDiag`** (protocol_state.rs), one per connection, made where its `connection_id` is bumped (`ProtocolState::new_diag`; the reload-restore sites `diag_for_reader`), dropped by `ProtocolState::clear`, carried to the tasks by `TelnetConfig::diag` - never by an `AppEvent`, so no reader test or event loop changes for it. The session records `TelnetNote`s only while `cfg.diag` is set (no clock: the reader stamps them in `record_read`), the reader counts bytes read and hands the writer the record with `WriteCommand::CountInto` (sent only with a diag), the connect task sets the peer and TLS version, and Clay's own sends (NAWS, CHARSET, GMCP hello, MSDP LIST) are noted by `ProtocolState::note_sent`. A reload keeps it (`protocol_diag=` JSON, `SavedDiag`, marked `reloaded`: the new session's option table starts empty) with `World::connected_at`. The run's start and restart count cross restarts in `CLAY_STARTED_AT`/`CLAY_RESTARTS` (`platform::pass_start_to_successor` at every exec/crash restart), believed only by a `--reload`/`--crash` successor. Memory and the rest come from `platform::process_stats` (/proc on Linux/Android, `proc_pidinfo` on macOS, hand-declared kernel32 on Windows). MUD-supplied text in the report goes through `stats::sanitize_and_cap`; the password never appears.
- **`reachability_json` is rendered, never recomputed.** `/reach`, the TUI Remote Access popup (`popup/definitions/remote_access.rs`), app.js's `showRemoteAccessDialog` and Android all display the one `reach::ReachabilityInfo` blob the server builds; a UI that computes its own addresses or verdicts will disagree with the others. Two traps behind it: the Windows Firewall verdict is "what wins for clay.exe", not "does our named rule exist" — cancelling the first-run alert leaves a *Block* rule named after the exe, and Block beats Allow, so `firewall::query_firewall_status` scans every inbound rule for the program and `add_firewall_rule` deletes them all before adding ours; and `port_map_enabled` is deliberately **not** a field of `UpdateGlobalSettings` (it travels only via `WsMessage::SetPortMapping`), because a 45-field settings save from an older client that doesn't know it would silently reset the toggle. The TUI popup's report is a *disabled* multiline field on purpose: a focused multiline field is drawn scrolled to its cursor at the end of the text, which would hide the LAN address.
- **Fonts are kept per program and OS** (`src/font_profile.rs`, user ruling 2026-10-17): a profile (the whole Font tab: font, phone/tablet/desktop sizes, weight, line height, letter/word spacing) per `<program>-<os>` key - `native-<os>` (`font_profile::native_key`, from the GUI's own build), `webview-<os>` (the WebView page is told `window.CLAY_GUI_OS`; Termux's WebKitGTK says Linux), `browser-<os>` (from the user agent), `app-android` - in `Settings::font_profiles`, settings.dat `[global]` lines `font.<key>.<field>=`. A key without one uses the shared `font_name`/`web_font_*` fields, which a client that knows profiles never changes: it echoes them back as sent (native `settings_update`, app.js `sharedFontToSend`) and sends its own as `UpdateGlobalSettings.font_profile` (`None` = unchanged; app.js sends one only once it has a profile or its fonts differ from the shared ones, so merely saving Settings doesn't create one). `GlobalSettingsMsg.font_profiles` is `None` from a server before the split - the client then edits the shared fields, as before (`set_font_for`). Read fonts through `GlobalSettingsMsg::font_for(key)` (native) / the font variables `receiveFontSettings` fills (app.js), never the shared fields directly.
- **The bundled JetBrains Mono has every weight from 100 to 800 in both GUIs** (user report 2026-11-01: "adjusting the font weight doesn't seem to have any effect"). The web's is one variable woff2 (`jetbrains-mono-latin-wght.woff2`, Google Fonts' latin subset, `@font-face` `font-weight: 100 800`; the one before covered only 400-800, so nothing below 400 changed, and it is served `immutable`, which is why a new font needs a new file name). The native GUI bundles all 16 static faces (`fonts::BUNDLED`, upright and italic per `BUNDLED_WEIGHTS`): GPUI applies no variation axis, so a variable font draws only its default instance. The native GUI asks for a weight JetBrains Mono has, chosen as a browser chooses (`fonts::css_weight_match`), so every platform's matcher agrees; a user font gets the raw weight. Most system fonts (`monospace`: DejaVu Sans Mono, Consolas, Courier) have only regular and bold, so there the weight can only switch between the two - in a browser too. **The Weight stepper offers only the weights the chosen font comes in, by name** (user request 2026-11-01; `font_profile::WEIGHT_NAMES`/`weight_label`/`step_weight`, app.js's copies pinned by a test; the setting stays a number): the native GUI reads the faces from a `fontdb` of the system fonts (`fonts::weights_of`, loaded once on a thread at start; a variable font is one face there), the web page finds them by drawing a sample at each standard weight and grouping identical renders (`measureFontWeights`), since a browser can't list a font's faces.
- **The Android app's bundled server (`--local-server`) must never start a subprocess.** Under the app, a spawn hangs it at random: `App::new`'s `which espeak` stalled about half the emulator's cold starts, so the server never listened and the app opened blank, without the splash. Every probe is gated on `LOCAL_SERVER_LOOPBACK_ONLY` (spell.rs aspell, `tts::detect_tts_command`, `audio::detect_external_player`, `cert_hostname`); gate any new one the same way. The server listens on loopback only unless the app's **Allow Other Devices** is on (Settings > Clay Server, Run on This Phone; off by default, confirmed first; `LocalServerManager.KEY_LAN_*`, started with `CLAY_LOCAL_SERVER_LAN=1` → `LOCAL_SERVER_LAN`): then every interface, the user's password and a fixed port - whose start waits for the port to come free, since the server just stopped for the restart holds it for a moment. `ReachabilityInfo.local_only` makes the Remote Access panels say only this device can connect.
- **The Android app with a keyboard AND a mouse draws the desktop GUI's chrome** (app.js `desktopInputAttached`, `body.desktop-input`; Java reports the mouse via `InputManager`, the keyboard via the Configuration): no button row, the menu and font slider on the separator bar, the icon bar, the scroll bar, Emoji Picker in the menu. Only the chrome: font sizes, input height and dialogs still follow the screen's device class. Its rules follow the phone/tablet ones in style.css at equal specificity, so they win.
- **The input height is split by interface.** The console's is `App::input_height` (TF's `%isize`, settings.dat `input_height`); phone, tablet and desktop clients each have their own in `Settings` (`input_height_phone`/`_tablet`/`_desktop` - the browser's device classes; the native and WebView GUIs are desktops, as for the font sizes). On the wire `GlobalSettingsMsg` carries all four (0 = a server before the split; a client then uses `input_height`) and `UpdateGlobalSettings` carries the three as `Option` (`None` = unchanged, which is what an older client sends). A settings.dat without the three keys seeds them from `input_height`, so nothing moves until one interface is resized.
- **New settings travel in `websocket::SettingsAdditions`** (`tabs_profile`, `screen_reader_profile`, `announce_screen_reader`, `status_panel`), the last parameter of `App::update_global_settings`, instead of yet another positional argument; tests pass `Default::default()`. A per-interface setting follows the Text Reveal/TTS pattern: the shared field stays what older peers read, a `BTreeMap<key, value>` profile per interface key (`valid_interface_key`), `GlobalSettingsMsg.<x>_profiles: Option<..>` (`None` = a server before the split, the client edits the shared field) and `UpdateGlobalSettings.<x>_profile: Option<InterfaceChoice>` applied only under the sender's own key. **Icon Bar** is one too (user request 2026-11-04): `Settings::icon_bar_profiles` holds `IconBarPlace` (= `TabsMode`: Top/Bottom/Left/Right/None); the shared `icon_bar` stays the old `IconBarMode` (None/App/Tablet/All), never changed by a client that knows profiles, and is where a client without its own takes its place (`GlobalSettingsMsg::icon_bar_for(key, legacy_shows)`, app.js `sharedIconBarPlace`: App/Tablet = Top in the GUIs, a tablet and the Android app with a keyboard and mouse, else None), so nothing moves until an interface picks. The bar is always outside the tabs: Top before them, Bottom between a bottom tab strip and the status bar, Left/Right the outermost column (native `icon_bar_column`, app.js `.icon-bar-vertical`, which scrolls whole and has no arrows). **Tabs** is one (user ruling 2026-11-01): `TabsMode` Top/Bottom/Left/Right/None (`OPTIONS`, `is_side`), `Settings::tabs_for(key)`; a side column sits in each GUI's output row (native `tabs_column`, app.js `#main-row` > `#output-column`), the map pane between the output and a right column. The split's top pane bar shows the same More/Hist indicator as the main bar (console `rendering::status_indicator`, native `more_badge`, app.js `paneMoreHist`).
- **Screen Reader is per interface; MUDs: Screen Reader is global** (`docs/markdown/24-accessibility.md`). With an interface's own on (`Settings::screen_reader` for the console, `screen_reader_profiles` for the rest, `App::client_screen_reader`): Text Reveal is off there (`Settings::console_text_reveal()`), `speak_arrivals` skips it (its screen reader reads), the console drops the clock and parks the cursor on the input, and new lines are announced **only from the paths that add a line to the screen** - app.js `announceLine` from `appendNewLine`/more-mode releases into `#sr-announcer`, the native `a11y.rs` live Status node - **never from a re-render** (a world switch, resize or filter would read the whole screen again); gagged lines never. `#output` is `role=log` with `aria-live=off` for that reason. `announce_screen_reader` sets MTTS bit 64 through `telnet::set_announce_screen_reader` (an atomic `TelnetConfig::default()` reads; thread-local under `cfg(test)`), at the next connect. The GUI and Android turn an interface that never chose on once when a screen reader is detected (native `sr_detect`, Android `isScreenReaderOn`).
