# CPU performance: what was measured, and the rules that came of it

Design record for the CPU investigation of 2026-11-22/23 (v1.7.39) and the fixes shipped as v1.8.1 (user request: "investigate clay from a cpu performance perspective with the whole codebase to see if its as reasonably efficent as possible", then "do the performance fixes"). Claude Code loads this file when one of the paths above is read or edited. `.claude/rules/native-gui.md` holds the earlier output-speed round's rules (the bench, the trace, the native GUI's caches); this file is the server, the two consoles, the web page and the build.

**How it is measured.** `perf` is blocked on the development machine (`perf_event_paranoid=4`), so: CPU nanoseconds and voluntary context switches per thread from `/proc/<pid>/task/*/schedstat` and `status`; callgrind unpacked from its `.deb` for attribution (`valgrind.bin --tool=callgrind --instr-atstart=no`, `vgdb instrumentation on`); a flood MUD (N lines at once, or one line per packet at a set rate) into a release musl `clay -D` with one WebSocket client; the console and the SSH console in a pty with a small screen model; the web page in headless Firefox through geckodriver's HTTP API, reading the content process's main-thread CPU and `requestAnimationFrame` gaps. `-D` runs no startup actions (a client's `ConnectWorld` connects a world), and on `-D` world 0 always counts as watched, so an unwatched-world run floods world 1. Every number below is a median of three on that machine; compare runs made back to back, never against these.

- **Rows are counted only while more-mode is on** (`World::add_output`, `counting`). Measuring a line's rows wraps the whole line (`RowMetrics::rows_as` → `display_wrapped_as`), and with more-mode off the count was only added to `lines_since_pause`, which nothing then read: 37% of the server's work per line. Worse, for a world nobody viewed the count stayed at the page size, so the "recount the bottom screenful" block re-measured about a screenful of old lines on **every packet** (main thread 88 µs a packet against 26 for a watched world). With more-mode off nothing is measured: the recount, the two partial-line adjustments and `rows_as`. **Switching more-mode on resets and recounts nothing** (user ruling 2026-11-23: "Switching on the more mode should not get a fresh page. It should just start the counting of lines that are used as part of the more mode"): each world's count stands where it was (a sent command or a release still zeroes it) and rows are added from that moment, which is what the web page and the native GUI already did with their own counts. Result: a plain burst 5.8 → 4.0 µs a line, the unwatched world 135 → 73 µs a packet. A new reader of `lines_since_pause` must not assume it was kept while more-mode was off.
- **A TF `-T` pattern is compiled once per thread** (`tf::macros::with_world_type_regex`, the `WORLD_TYPE_PATTERNS` thread-local, keyed by matching style and pattern, 256 a style). `world_type_matches` runs for every `-T` macro on every line and every hook fire, and compiled its pattern each time, twice for a glob: 30 triggers of which 10 had `-T` cost 6,158 µs a line against 11 for 30 without; now 7.9. Keyed by what the regex is made from, so `/edit`, a new `-m` and a reload need no upkeep. The regex is lent to a closure, never cloned (a cloned `Regex` starts with an empty cache). Left alone because they measured as noise: `compile_hook_pattern` (twice per fired hook), `engine.world_types`, the per-line sort of trigger macros.
- **`is_match` before `captures`** in the two per-line matchers (`actions::check_action_triggers_plain`, `tf::macros::match_trigger`): nearly every line matches nearly nothing, and `captures` runs the capture-group search and allocates. 30 actions and 30 triggers: 14.0 → 9.1 µs a line (with the row count gone).
- **The machine's address list is kept a minute** (`reach::local_ipv4_addrs`, `LOCAL_ADDRS_TTL`; `still_fresh` is the rule). Listing it runs a subprocess on every platform (`hostname -I`, `ipconfig`, `ifconfig`), `build_reachability_info` asks for it, and `build_global_settings_msg` asks for that: so every login, every settings broadcast, on the event loop. Each login stalled the whole server 52 ms; now 1.4. `reach::forget_local_addrs` at the explicit refreshes (`/reach --refresh` before the report is built, `request_reachability_refresh`). The certificate's own listing (`get_local_ip_addresses`) is not cached: it runs at start only. And **`util::run_command_capture` waits in steps that grow from 1 ms to 50** (it slept a flat 50 ms before looking, so a 2 ms tool cost 50).
- **The archive writer sleeps while it has nothing queued** (`scrollback::WriterMsg`): `recv` with no timeout when its batch is empty, `recv_timeout(until the flush is due)` when it isn't. It woke every 50 ms for the life of the process, 20 times a second, to look at a shutdown flag; `flush_and_close` now sends `WriterMsg::Wake`. **Its two inserts are `prepare_cached`**: parsing them per row was two fifths of the writer's work (archive on: 17.8 → 12.5 µs a line).
- **The GUI reload flag wakes its loop** (`GUI_RELOAD_NOTIFY`, a `tokio::sync::Notify` as `GUI_QUIT` is): the headless loop polled `GUI_RELOAD_REQUESTED` every 100 ms in every GUI's in-process Clay and in the Android app's bundled server, which never sets it - 40 wake-ups a second, now none. Whoever sets the flag notifies.
- **The keepalive's "is `next_seq` above the buffer" check doesn't walk the buffer** (`World::highest_held_seq`): the paged-in archive prefix is scanned (made-up seqs in several runs), then the last live line and the last held line. 2.7 ms per client per keepalive on a million-line session, now 0.17. Under `cfg(test)` every call is checked against the plain scan.
- **The consoles pace the draws that network and app events ask for** (`rendering::DrawPacer`, `DRAW_PACE` 16 ms; a pure struct, one per loop). A burst was already one draw (the loops drain what is queued), but text arriving a line per packet drew everything per event: `terminal.draw` plus a repaint of the output area. Such a draw now happens at once when the last paced one was at least a frame ago and is otherwise **owed**, with a timer (`draw_sleep` in `run_app`, `draw_due` in `run_console_client`) that brings the loop back, so the last line is never left undrawn. **Urgent** causes never wait and take an owed draw with them: terminal input (keys, paste, mouse, resize), the keepalive/prompt/process/reveal timers, `needs_terminal_clear`, a popup coming or going, a `terminal.clear()` after a splash clear, a turn that ran `run_terminal_ops`. A draw for input alone opens no frame, so the first reply after a keystroke is drawn at once. A new cause of a draw is paced unless there is a reason it can't wait.
- **Only a world on the console's screen asks for an output repaint** (`App::console_shows`: either pane). `add_visible_run` and `handle_telnet_event`'s stats set `needs_output_redraw` for any world; a busy world in the background cost the console a whole repaint per packet. Two things that had been relying on that: the two `terminal.clear()` sites after a splash clear (`World::needs_redraw`) now set `needs_output_redraw` and an urgent draw themselves - without that a background world's first text would blank the screen; and a gagged run under F2 sets the flag for a shown world (`add_gagged_run`). `add_output_to_world`, `emit_client_lines_marked` and `handle_disconnected` ask `console_shows` too (they asked `current_world_index`, missing a split's other pane).
- **The SSH console draws what a message changed** (`App::remote_message_draw` → `RemoteDraw`, asked before the message is applied): nothing for text, stats or held-line counts of a world in neither pane, an unchanged `ActivityUpdate`, `UnseenUpdate`/`UnseenCleared`; the bar alone for a new activity count; everything for whatever isn't named, as before. It drew everything for every message, twice a packet (each packet's text is followed by an `ActivityUpdate`). Its loop keeps two kinds of draw: `needs_redraw` (input, timers: at once, and the output pass always - its key paths were written against always-repaint and set no flag) and `ws_dirty` (a server message: paced, the output pass only when `needs_output_redraw`, a popup change or a clear asks). `reveal_due` is set only by an output pass that ran.
- **The web page rebuilds its bar once a frame after the server's counter messages** (`statusBarSoon` in the `UnseenUpdate`, `UnseenCleared`, `ActivityUpdate` and `PendingLinesUpdate` handlers; at once while `document.hidden`, where no frame comes; `ActivityUpdate` calls `reportBadge()` itself so the taskbar badge never waits). Each rebuilt the whole bar on the spot and read the layout while the lines just inserted were unlaid-out: a layout per message, two or three messages a packet. With the palette below, the page's main thread: 0.82 → 0.54 ms a line at 200 lines a second, 0.58 → 0.20 at 1,000, and 0.27 → 0.12 ms a packet for a world it isn't showing. `the_web_page_rebuilds_its_bar_once_a_frame_and_reads_the_palette_once` pins both.
- **The web page reads the theme's ANSI palette once per theme** (`ansiPaletteKept`, `forgetAnsiPalette` in `applyThemeColors` and `applyThemeAppearance`, which every writer of `#theme-vars` calls). `parseAnsi` read the 16 CSS variables through `getComputedStyle` for every coloured line. The two variables are declared near the top of the script, before the theme functions can run at start; and never assign `parseAnsi`'s own locals from outside it (that once threw under strict mode on every theme change).
- **The clock's text is set only when it changes** (`updateTime`, every second).
- **The build.** The static Linux builds (`target_env = "musl"`: the x86_64 and ARM64 assets, the Drobo build) use **mimalloc** as the global allocator (`Cargo.toml` target dependency, `#[global_allocator]` in main.rs; `--version`'s Features line says `mimalloc`): musl's own `malloc` was 27% of the work per line and now and then fell into a slow mode (half the run in `mmap`/`munmap`). Every other platform keeps its own allocator. It costs memory: 132 MB against 62 after a 200,000-line burst, 34 against 23 after 20,000 lines (the user's choice, 2026-11-23). And **`[profile.release]` is fat LTO with one codegen unit** (the musl build 40 s → 3 min 40 s, 36.0 → 25.9 MB); a builder that can't finish with it builds that asset with `CARGO_PROFILE_RELEASE_LTO=thin` and the release summary says so.

**What it came to** (µs of server CPU per line or packet; v1.8.0 → the code fixes → with mimalloc → with fat LTO too):

| Run | v1.8.0 | code | + mimalloc | + LTO |
|---|---|---|---|---|
| 200,000 lines at once | 5.79 | 4.26 | 3.32 | 2.05 |
| the same, coloured | 7.77 | 5.54 | 4.02 | 2.43 |
| one line per packet, 2,000 a second | 75.2 | 68.0 | 69.8 | 57.6 |
| the same for a world nobody views | 135.5 | 71.6 | 71.1 | 60.9 |
| 30 actions and 30 TF triggers | 13.96 | 9.13 | 7.80 | 6.34 |
| 30 TF triggers, 10 with `-T` | 6,158 | 7.86 | | |
| archive on | 17.84 | 13.14 | 9.04 | 7.43 |

Console, one line per packet at 2,000 a second: 273 → 47 µs a packet, 58 MB of terminal output → 2 MB; at 200 lines a second 348 → 120 µs a line; a flood on a world not shown 263 → 46 µs a packet and 9.4 MB → 19 KB drawn. SSH console: 541 → 48, 598 → 123, 495 → 48 (25 MB → nothing drawn). A key typed during a flood is echoed within a millisecond, before and after.

**Found while checking, not changed:** the console prints "✨ Connected!" only when `AppEvent::ConnectionSuccess` is handled by `run_app`'s batch-drain loop, never by its select arm (the drain copy's own comment says so), so the line has always come and gone with timing; a faster build shows it less often on a world that connects within a frame. Reported to the user 2026-11-23.

**Tried and taken out again: inserting the shown world's lines once a frame instead of once a message** (a `frameBatch` that `endAppendBatch` parked and the scroll frame flushed, with a `flushFrameBatch()` in front of every other writer of the output's lines). Built, checked for order and completeness in headless Firefox, and measured after the bar and palette fixes: nothing at 200 lines a second (2,236 ms against 2,179), 6% at 1,000, 3% on a burst. The browser already lays out once a frame once nothing reads the layout in between, so what remained was per frame, not per line. Not worth a standing rule that every new writer must flush first; don't redo it without a profile that says otherwise.

**Measured and left alone** (noise, or not worth its risk): decode's four passes; TF hooks and `sync_tf_world_info`; the session log; the per-client JSON copy; `ActivityUpdate` per packet on the wire (it shares the socket write with the text; sending it only when a client's count changed needs per-client state); `waitpid` per loop turn; more-mode holding and releasing; `InitialState`'s buffer scans (18 ms at a million lines); the web page's F4/F5 typing and more-mode release; the native GUI's per-frame walks; thin LTO (1-5%). **Not done:** the native GUI's idle wake-ups (about 68 a second, cause not profiled); the server's uncapped line buffer (268 MB per million lines: memory, a past decision); the web page's ResizeObserver invalidating its view metrics on every append (cheap once the bar and the insert are per frame, and skipping it risks a stale `UpdateViewState`).
