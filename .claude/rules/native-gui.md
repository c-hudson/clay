# Native GUI (GPUI) and the desktop GUIs

Design record for the native GUI's windows, menus, taskbar, more-mode, scroll bar, glyph fitting, row counts and the output path's performance rules. Claude Code loads this file when one of the paths above is read or edited; CLAUDE.md ("Rules That Bite Everywhere") keeps each rule as one sentence with a pointer here. The text below is the full detail, history and function names, moved verbatim from CLAUDE.md on 2026-11-08.

- **Native GUI: `ClayView::after` applies the core's effects itself.** A `core` call (`self.session.core.x()`) returns effects - `Effect::Send` among them - and `after` runs them through `Session::apply` (which is what sends, or hands a follower's message to its leader) before showing the rest, so `self.after(self.session.core.x(), cx)` is complete on its own and the older two-step `let rest = self.session.apply(fx); self.after(rest, cx)` still works. Before this, `after` only knew display effects: a shell world's keys (`shell_key`/`shell_text`/`shell_paste`) went to it unapplied and were never sent, in every build from v1.7.0 to v1.7.5 - the prompt showed, typing did nothing.
- **Native GUI: the hamburger is also the desktop's app menu** (user request 2026-10-31, `ui/appmenu.rs`; the WebView GUI has none by user ruling). One list and one rule: chrome.rs `MAIN_MENU` and `menu_sections`/`menu_shows` (Change Password and Logout only on a multiuser server, Edit World only on a single-user one, Import Picture only where it uploads), then Quit; a choice runs `ClayView::menu_action` as a click does. macOS: `cx.set_menus` with one `MenuCommand(id)` action, handled by the active ClayView's root (`appmenu::listen`), else by the main window (a global `on_action`). Linux: GPUI stores `set_menus` but never publishes it, so Clay speaks GTK's own protocol over zbus (already built through GPUI → ashpd): one `org.gtk.Menus` model holding every item (`hidden-when: action-disabled` on the ones some server lacks, `chrome::menu_always_shows`; the model and the Windows ids cover `every_menu_section`, never one server's view) and an `org.gtk.Actions` per ClayView window, named on the X11 window by `_GTK_UNIQUE_BUS_NAME`/`_GTK_APP_MENU_OBJECT_PATH`/`_GTK_WINDOW_OBJECT_PATH`; vala-panel-appmenu (xfce4/MATE/Budgie) then shows it under the program's name in place of its own New/Quit stub. KDE Plasma's Global Menu reads the same properties through `gmenu-dbusmenu-proxy`, which skips a window without `_NET_WM_WINDOW_TYPE_NORMAL` - GPUI leaves the type unset, so `Props::set` writes it (found with the real proxy, 2026-10-31). Nothing is drawn in the window; no bus, Wayland or no applet means nothing happens. The same list (less Quit) is the macOS Dock menu (`cx.set_dock_menu`, routed like the menu bar) and heads each ClayView window's Windows system menu (`appmenu::win`: `SetWindowSubclass`, command ids `items::command_id` = multiples of 16 below 0xF000, the subclass only forwards `WM_SYSCOMMAND` and frees its box at `WM_NCDESTROY`); Alt+Space never opens that menu in Clay (it is `collapse_spaces`), a title-bar right-click does. **A choice reaches its window by the window's handle, never `update_in`**: GPUI resolves `update_in` to the window that last drew the entity, and a `/window` draws reading its leader's view - a choice in the main window's menu went to the follower's window, and none came through once that follower closed (found live, 2026-10-31).
- **Both desktop GUIs reach the taskbar through one module, `src/desktop.rs`** (user request 2026-10-31; console, browser and Android excluded by ruling). Taskbar Alert (`Settings::taskbar_alert`, off by default, shown only in the two GUIs' Settings; `UpdateGlobalSettings.taskbar_alert: Option`, `None` from every other save): text from the MUD - live `ServerData` that isn't gagged, or a rise in a world's `pending_count`, since the server's more-mode holds lines without sending them - while no Clay window has focus asks for attention once (`desktop::alert_once`, reset by any Clay window gaining focus: native `taskbar::watch` on every ClayView and popup, the WebView's `WindowEvent::Focused(true)`). Native: the core's `take_live_text`, read only by the window with the connection (follow.rs `handle`), then GPUI `request_attention` by window handle; GPUI clears X11's urgency only on `_NET_WM_STATE_FOCUSED`, so `taskbar.rs` clears it itself. WebView: app.js `desktopHostSend` (`alert`, `badge:<n>`, `notify:<json>`, never from a popup/grep/notes page), the host taking the badge and `/notify` only `from == main_window_id` (every window's page has its own connection). The badge is the ACT count: Unity `LauncherEntry` on Linux (served with `Query`; tao's own needs libunity), `ITaskbarList3::SetOverlayIcon` on Windows, the Dock tile on macOS. `/notify`: `org.freedesktop.Notifications`, a toast from the AppUserModelID `Clay` (registered under HKCU on first use, as GPUI does), `osascript` on macOS (a bare binary has no other way). Docks match a window to `clay.desktop` by class, so both GUIs name their windows `clay` (native `set_app_id`, the WebView `glib::set_prgname` + `gdk::set_program_class`) and `desktop::ensure_desktop_file` writes `~/.local/share/applications/clay.desktop` when missing, or when it is Clay's (`X-Clay-Generated=true`) and says something else; never someone else's, never from a cargo `target` build.
- **Native GUI: what `ClayView::later` queues runs at the window's next frame, so a close must be queued too, never decided by `is_open` at call time.** Dialogs open through `later` (they need the main window's `Window`); `close_dialog` used to queue a close only if the dialog was already open, so a reconnect that went connecting → online between two frames (a few ms on a LAN; a background window draws even less often) skipped the close and then opened "Connecting to Clay Server" over a working connection for good. The snapshot harness can't show such races by itself (headless GPUI draws whenever it settles): `open:connect-race` feeds the two states with no frame between; `tick:` runs the view's clock and `peek:` reports without drawing.
- **Native GUI: a `/window` (follower) shares the main window's connection, so the server sees one client with one world on screen.** A follower's `MarkWorldSeen`/`UpdateViewState` are dropped (`session::is_upkeep`) - sending them would move the main window's view, history and ▶ claims - so the main window reports its followers' worlds instead (`ClayView::report_other_views` → `OtherViews` → `App::handle_other_views`, a per-client `ws_client_other_views` that `ws_client_viewing` consults; a newly listed world is `mark_seen`). Without it a world brought up in a follower stayed unseen on the server, and Unseen First sent the follower back to it from every other world: Up/Down there bounced between two worlds and never reached the one with activity. It goes only to a server whose `InitialState.other_views` is true: **a server closes the connection on any message it can't parse** (`WS-BAD-MESSAGE`, then `break`), so a new client→server message sent unconditionally - and re-sent after every login - would keep a new GUI disconnected from an older server. Gate any new one the same way.
- **Native GUI more-mode (`ui/more.rs`): scrollback replies are never arrivals, nothing is drawn below a held line, and it counts rows.** A cold start from the disk cache takes the newest lines InitialState carries straight into the kept buffer (`client.rs` `merge_newest`, app.js `mergeNewestLines`, flagged as scrollback) and gap-fills only the hole below them (`World::holes_only`/`_holesOnly`: the catch-up stops once no hole is left, never asks past them; a resync's named range is still owed whole) - catching up from the cache's end instead appended everything that arrived while the client was closed at the bottom, 500 lines a reply, and the view scrolled through all of it (user report 2026-10-26). A gap fill's lines still land at the tail on a reconnect without that slice - so every line from a scrollback reply carries `Line::scrollback`, and `MoreMode::arrivals` neither counts nor pauses on it (app.js's gap-fill branch bypasses `handleIncomingLine` the same way); without it the ~300 lines that arrived while the GUI was closed paused after a screenful and the window opened hundreds of lines back. Once paused, every line is held (client lines too, as app.js queues them) and `visible_lines` stops at the first held line: holding only the MUD's lines left an action's `/echo` lines drawn below the hold, pinned at the bottom while Page Down released lines in above them ("half a window at a time, the bottom half unchanged"). The pause threshold and releases are row budgets (`core::wrap::rows_in_columns`, the layout's wrap in whole columns), and a release spends this window's own held lines before asking the server (`ReleasePending`) for the rest. app.js follows the same two rules (`handleIncomingLine`/`releaseLines`, rows from `lineRows`, the server's own estimate of a line at the client's width): before, it paused and released by LINES - a screenful of wrapped prose overflowed the view - and asked the server in the same press it released its own, whose `PendingReleased` (a LINE count, still honoured: another interface's release shows as many held lines here) then released that many more. **More-mode is per world in both clients, as on the console** (`ClayView::more`, a `MoreMode` per world name, fed for every world in `follow_world`; app.js `worlds[i].more` via `moreOf`): every world's arrivals are counted and held in the viewer's own rows whether or not it is on screen, a switch shows the world's own held state, leaving a world counts afresh only when it holds nothing (`MoreMode::left`, the console's `switch_world`), and nothing is held at a connect (the server's `pending_count` stands in, so the cold-start rule above still holds). Before this only the shown world was counted and a switch dropped the hold, so a 50-line backlog came out all at once on the phone (user report 2026-10-23); the server pages a world nobody views against the console's screen (`viewer_output_dims`), which is why the client's own hold is what pages it.
- **The output's scroll bar is drawn the same everywhere on a desktop** (native `ui/output.rs`, every window; style.css `body.device-desktop #output-container`): an 8px thumb 1px from the edge in fg-muted (fg-secondary under the mouse), no track, its strip reserved even when nothing scrolls so the text never rewraps on the first overflow. Two traps. In the browser engines, the standard `scrollbar-width`/`scrollbar-color` beat the `::-webkit-scrollbar` pseudo-elements wherever both are known: left set, WebKitGTK (the Linux WebView GUI) drew GTK's own 21px trough, so they are unset under `@supports selector(::-webkit-scrollbar)` and only Firefox keeps them. In the native GUI, a thumb drag *replaces* `Scroll::pending` (`drag_thumb_to`): the thumb's place is absolute, and two mouse moves between frames, each measured from the same last layout, used to add up. The thumb's total counts lines not laid out yet by `rows_in_columns`, cached per width (`Scroll::estimates`), not as one row each.
- **Output is a grid in the GUIs too: cells, and a symbol whose glyph isn't one cell wide is fitted to one.** Box drawing (U+2500-257F), block elements (U+2580-259F) and spaces on a background are drawn as exact cells (app.js `renderBlockElements`, native `core::style` `Cell`). Every other symbol, punctuation mark, "other number" or Greek letter above Latin-1, one column wide and outside the right-to-left scripts (`core::style::glyph_fit_candidate`, app.js `EMOJI_TEXT_OR_FIT`, pinned together by `app_js_fits_the_same_symbols`), is measured in the output's font and, when its advance is more than a thousandth off a cell, drawn in a box exactly one cell wide, centred, at a smaller size if wider (app.js `glyphFitStyle` → `.gfit`, measured once per font at 100px against '0' and re-measured on `document.fonts` `loadingdone`; native `glyph_fit` → `LaidLine::fit`, from the advance it shaped, via `fixed[i]` and `paint_glyph`'s size). The bundled JetBrains Mono is a Latin-only subset, so most of what the FANSI decoder emits (☺♥☼►▲∟⌂, Greek, math, ■) comes from the OS's fallback font, which ends every font choice's stack: on Android ■ was 1.25 cells and ☼ 1.53, and every FANSI row holding one ended to the right of the rest whatever font was picked (user report 2026-10-25, reproduced from the user's `/dump` in the emulator's WebView). A 2% tolerance was too loose: 80 symbols at 1.019 are a column and a half off. The console needs none of this - a terminal is a grid. `tests/native_gui/corpus.ans`'s "FANSI symbols" section is the check: every row must end where the row of zeros does.
- **The output path has a trace and a bench, and these are its rules** (user report 2026-11-06: `clay --gui=<host>` on a LAN showed a flood late, in bursts). `CLAY_NATIVE_PERF=1` makes the native GUI write one line a second to its debug.log (`core/perf.rs`: messages per wake, `apply_settings`/`follow_world`/`prepare`/`paint` times, lines held, the latency from the socket to the frame); `CLAY_SNAPSHOT_BENCH` has `CLAY_SNAPSHOT_BENCH_PREFILL=N`, `_BG=1` (a background world) and `_BURST=N`; `reference/fake-mud-server.py --flood N --rate L` floods a world. What they found, and the rules that came of it: **native GUI** - `apply_settings` runs only when `settings_rev`/`actions_rev` change (on every message it re-read the font tables - with `monospace` two `fc-match` spawns a message, 15 ms a line - and serialized the actions to compare them); `Fonts::set_user` looks faces up only on a change, `system_monospace`/`emoji_family` are asked once; `Textdiv::note_worlds` walks only lines newer than `Mark::scanned` (it re-walked every live line of an unvisited world per message); `World::lines` is capped at `MAX_LINES` (10 000; `World::trim` from the two tail-push paths, never while the view is scrolled back in that world - `ClayView::report_pinned` → `set_pinned` - after which history starts at the oldest kept line, `history_done` is reset, and the holes below it are closed in `seen` so no gap fill asks for lines it would drop again; every frame walked the whole buffer, 17 ms at 100k lines); `visible_lines` builds its `seqs` only during a textdiv visit and the selection's id map lazily (`SelectState::order`), `reveal_snapshot` walks `reveal_at` rather than every line when no switch is fresh; `Scroll::laid` keeps each line's `LaidLine` between frames, keyed like `rows` by the styled line's identity plus `emoji::generation()` for a line with a Discord emoji. **Server** - the writer `feed`s everything queued and `flush`es once (`WS_WRITE_BATCH_MAX`); `WS_CLIENT_CHANNEL_CAPACITY` is 1024 and `websocket::log_channel_full` writes `WS-CHANNEL-FULL` at most once a second per client; a run of gagged lines is one `ServerData` (`add_gagged_run`); `process_triggers` strips ANSI once (`check_action_triggers_plain`, `process_line_plain`) and borrows `settings.actions` (a cloned `Regex` starts with an empty cache); TF sorts only the macros with a trigger; `wrap_urls_with_osc8` compares in place (it was quadratic); the per-world log is a `BufWriter` written out by `App::flush_logs` once per loop turn, at `/quit` and in `save_reload_state` (an exec runs no destructors); `gui_tx`'s receiver is dropped at start in every in-process GUI (nothing ever read it, and a clone of every broadcast queued there for the life of the process) and the clone is skipped once `is_closed()`. **Web** - `viewMetricsFor` caches a container's rows and columns (invalidated by the ResizeObserver and the font setters; reading `clientHeight` after an insert forced a layout per line); a `ServerData` message's lines go into the DOM in one insert (`beginAppendBatch`/`endAppendBatch`); `trimOutputDom` keeps at most `RENDER_WINDOW_MAX` lines drawn while following the bottom; `scheduleStatusBar` coalesces the per-event callers; `escapeHtml` is string replaces, F8's patterns are compiled once (`actionRegex`). A new per-message or per-line step goes behind the same gates, and the bench and the trace are how it's judged.
- **The native GUI's row counts belong to the styled line they were measured from** (`output::RowCount`, a `Weak<StyledLine>` + rows, `cached_rows`). Keyed by line id alone, a count outlived the line's ▶ coming or going (a per-line restyle, not a global `restyle()`): a count too big made `prepare` index a row the new layout didn't have and ended the GUI (the user's three crashes 2026-10-19..27, "the len is 1 but the index is 1"), a count too small left a row undrawn. `prepare` also drops any `VisibleRow` past its line's rows before painting, logged once.
- **The native GUI's window zoom (`^+`/`^-`/`^0`) is per window and in memory only** (user request 2026-11-10; native GUI only by ruling - the WebView GUI has none and a browser tab keeps its own page zoom; shrinking below 1:1 allowed; Ctrl+0 resets). The rules are `src/zoom.rs` `ZoomState`, gpui-free and unit-tested in every build: 1.2× a level like xfce4-terminal (whose `terminal_screen_update_font` maps a level to Pango's scale table and resizes to keep the grid), levels -7..7, the window at level 0 is the `base` and every level is `base × 1.2^level` (proportional, not grid-exact: the fixed-px chrome means a fraction of a row a step), kept on the screen with the origin shifted only as far as needed, and **a window that would outgrow the screen becomes the screen** - the whole work area, not the one axis that overflowed (user report 2026-11-10: a height clamped alone left 265 px of the screen's left side empty), **a clamped level steps no further** (the user's "silently fail": level, text and window all stay), out from a clamped level is the previous size, 1:1 is the base exactly, position included; a maximized/fullscreen window changes only its text and is never a base. **Everything is in content coordinates and the window manager's frame comes off at the edges** (`zoom::Frame`): the screen a window may fill is the work area `inset` by the frame, and the platform is asked to put the frame at `outer` (the content's place less the frame's top-left) - X11 `_NET_FRAME_EXTENTS` (xfwm4's default theme: 4/4/23/4; none on a bare Xvfb, so the first Xvfb run never showed it), Windows DWM's visible frame around GPUI's client origin (`SetWindowPos` then also takes off the invisible resize borders it places by), macOS the frame's height over the content's (AppKit's bounds are the frame's, so `window_rect` adds the title bar). Without it every step walked the window down and right by the frame and a window grown to the screen hung its title bar's height off the bottom (user report 2026-11-10, the input's last line cut; reproduced and fixed with xfwm4 on Xvfb :97 plus a fake strut panel for a real `_NET_WORKAREA`: a step, a clamp, user moves between steps and Ctrl+0 all land exactly). `observed` (fed by `cx.observe_window_bounds`, which GPUI fires for moves too) tells our own change from the user's: a step sets `expected`, consumed only once the platform reports our size at our place (X11 reports the resize at the old place first and the move after it - the first report shifted the base's origin on Xvfb, so Ctrl+0 came back 20 px high; `SIZE_TOLERANCE` 1.5 px, `EXPECT_WINDOW` 1 s after which the place the platform left it at counts, for a WM that puts it elsewhere or Wayland), and the confirmed bounds are kept as `applied`: a later report of the same size and place is an echo, the same size elsewhere the user's move (the base moves by the same distance), another size the user's resize (the base becomes `size / scale`, so later steps scale the dragged size; before `applied` was kept, an echo at a clamped level re-based from the clamped size and a third Ctrl+plus grew the window to the whole screen, Xvfb 2026-11-10). `ui/zoom.rs` is the one caller: `ClayView::zoom` per window (followers and `--grep` windows zoom alone), the text drawn at `text_size()` = `font_size × zoom.scale()` by output (`OutputSnapshot.font_size`, whose row cache is keyed on it and re-lays out, as the slider relies on), input, find bar, split and splash - the chrome stays in px, the slider shows `font_size`, which the zoom never writes, so `apply_settings`, the preview and the slider's save are untouched. Keys: GPUI names Ctrl+Shift+= as `+` with Shift cleared on Linux, Windows and macOS, so the name is `^+` (keymap.rs also turns a shifted `=` into `+` and the keypad's `add`/`subtract` into `+`/`-` under Ctrl); the console's crossterm maps Ctrl+minus to `^7`, so the console never sees these (its arm is `KeyAction::None`); **never `^=` as a default** - keybindings.dat and `/bind` split a line at its first `=`. GPUI has no move API (`PlatformWindow` resizes only), so `ui/zoom.rs` moves the window itself: X11 `ConfigureWindow` on its own `RustConnection` (opacity.rs keeps its own for its ordering), Win32 `SetWindowPos(SWP_NOSIZE)`, AppKit `setFrameTopLeftPoint:` (origin flipped against the primary screen; `NSView`/`NSWindow`/`NSScreen`/`NSGeometry` features), Wayland nothing. GPUI's X11 "display" is the whole X screen, so the monitor is RandR's `get_monitors` under the window's centre cut to `_NET_WORKAREA` (x11rb `randr` feature); elsewhere `display.visible_bounds()`. The snapshot harness has `zoom:` (level, text size, viewport); the headless window honours `resize` but has no display and no bounds callback. app.js: the three `case`s return false (PARITY rows), and the document-level key handler `preventDefault`s a bound key only when it was handled or isn't in `ZOOM_ACTIONS`, so a browser's own zoom keeps working while the input isn't focused.
